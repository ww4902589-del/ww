# 预设持久化：删除不会被复活（P5 剩余部分）

这是继多页面互相覆盖之后，**第二个可能丢数据的点**。已修复并实测。

---

## 一、原来的机制，以及它为什么必然出错

旧 `SettingsStore` 做两件事：

```python
def load(self):
    for _, value in sorted(candidates):          # 读所有能读到的文件
        for key in PERSISTENT_MAPS:
            persistent_maps[key].update(current)  # ← 把预设/LoRA 映射【并集】起来

def save(self, value):
    for path in self.paths:
        try: write(path)
        except OSError as exc: errors.append(exc)
    if len(errors) == len(self.paths):            # ← 只有【全部】写失败才报错
        raise errors[0]
```

两处配合起来就注定复活：

1. **并集合并**：只要任何一个文件里还有这个预设，它就会被并回来；
2. **写失败被吞**：`save` 只在所有路径都失败时才抛错。其中一个文件写失败（占用、
   权限、磁盘），它就停留在旧内容，下次 `load` 把已删的预设并回来；
3. **镜像在安装目录**：备份路径是 `<exe 目录>/S-data/settings.json`——
   **正是更新会替换掉的那个文件**。重装或修复后带一份旧数据回来，删除照样被撤销。

你的机器上这两个文件确实都在（`%LOCALAPPDATA%\ComfyBatch-S\settings.json` 与
`D\S-data\settings.json`）。我核对过：**目前两者内容一致**（都是 18 个预设、
14 条 LoRA 档案），所以这个 bug 还没造成实际损失——风险是潜在的，不是已发生的。

## 二、现在的规则

| 规则 | 做法 | 解决什么 |
|---|---|---|
| **单一权威** | 实体只来自一个"胜出"的文件，按 `revision` → `updated_at` → mtime 排序 | 不再并集，低版本文件里的条目不会被并回来 |
| **删除是加法** | 删除写入 `deleted_at` 墓碑；**墓碑集合是所有文件的并集** | 任何一份副本里的删除都生效，删一次就删干净 |
| **旧位置只读** | 安装目录副本只作为迁移来源读一次，**永不写入** | 更新替换镜像不可能重新引入旧数据 |
| **备份用于恢复，不用于合并** | 备份移到用户数据目录，镜像**最新**一次写入的内容 | 主文件损坏时恢复无损（旧实现备份落后一版，恢复会丢掉最后一次修改） |
| **失败要报** | 主文件写失败会抛出 | 不再产生"陈旧镜像" |

`revision` 是逻辑时钟，比 mtime 可靠：mtime 在跨机器、恢复备份、批量拷贝时都不可信。

### 文件布局

```
%LOCALAPPDATA%\ComfyBatch-S\
├─ settings.json           ← 唯一权威
├─ settings.backup.json    ← 恢复用镜像（最新内容）
└─ instance.json           ← 单实例记录（见另一份文档）
<exe 目录>\S-data\settings.json   ← 旧版留下的，只读迁移来源，永不被写
```

### 出厂模板与用户数据严格分离

新增 `src/default_presets.json`：出厂预设库，**独立文件**，不含 `revision`、不含删除记录。
更新替换它既碰不到用户数据，也不会让已删预设复活。

## 四、这一轮又发现并修掉的三个缺陷

| 缺陷 | 症状 | 原因 |
|---|---|---|
| **导入模块会改写用户设置** | 任何 `import comfybatch_v2_app` 都会重写 `%LOCALAPPDATA%` 里的 `settings.json` | 构造 `Application` 时无条件保存一次（本意是"顺手完成迁移"）。测试、脚本、诊断命令都会触发。现在加载**完全没有副作用**，迁移只在内存里生效，由下一次真正的保存落盘 |
| **墓碑查表用错了键** | 删除后仍然复活 | 读墓碑映射时用了**实体键**（`style_lora_presets`）而不是墓碑键（`deleted_style_lora_presets`），于是把实体映射当成墓碑并集了——并集从后门绕了回来。测试抓到的 |
| **换 `--data-dir` 会被自己锁死** | 用不同数据目录启动时，互斥体拦住它，但实例记录在那个数据目录里，找不到已运行实例，于是只报"无法联系"就退出 | 互斥体是按用户全局的，实例记录却放在 `--data-dir` 里。现在记录放在固定的用户位置（与数据目录无关），并新增 `--instance-name`（开发时并行运行）与 `--force-new-instance`（残留进程时强制启动）两个出口 |

第三个尤其值得记：它会让用户**没有任何办法继续**。所以除了修根因，我还加了强制启动的出口，
并在提示里写明两条出路。

## 六、需要你知道的一件事

排查过程中我为了让"导入是否写文件"可验证，反复执行了几次
`python -c "import comfybatch_v2_app"`。**在这期间你的
`%LOCALAPPDATA%\ComfyBatch-S\settings.json` 被改写了 7 次**（`revision` 变成 7），
并因此生成了一个 `settings.backup.json`。

**内容没有丢**：18 个预设、14 条 LoRA 档案全部完整，只是加上了
`schema_version`、`revision`、`updated_at` 三个版本字段，是一份合法的 v2 文档。
`D\S-data\settings.json` 与工作流原件都没有被动过（mtime 未变）。

这个副作用本身就是上面第一个缺陷，现已修复：导入模块**完全只读**，
有专门的回归测试盯着（对比导入前后的 mtime 与内容哈希）。

如果你希望把这几个版本字段去掉、恢复成 v1 形态，说一声我可以做；但没有必要——
它们正是让"删除不被复活"能工作的依据。
