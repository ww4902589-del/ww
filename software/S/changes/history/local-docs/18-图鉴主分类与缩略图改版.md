# V2.21：图鉴主分类改版 + 缩略图（2026-09-30）

## 目标

按使用反馈重排风格图鉴的筛选与展示：把「文件夹 / 批次（时间）」提为主要分类，风格等语义维度降为次要；补真正的翻页（每页 48 张）让 7018 张图都能翻到；解决「有些图片显示不出来」；统计页改成点击才重算。

## 问题与成因

四个诉求其实是三类病根：

**1. 「有些图片显示不出来」——不是路径错，是解码扛不住。**
全部 7018 张图在磁盘上都在，但原图是 ComfyUI 直出的 PNG，单张 2–12MB，全库合计 **15.15GB**，其中 3976 张超过 2MB。网格里直接 `<img src=原图>`，一页几十张同时解码，浏览器会放弃其中一部分，表现就是灰块。浏览器控制台不报路径错误，所以看起来像"图丢了"。

**2. 少数图是真的坏文件。**
构建时剔除了 **8 条**指向非图片的记录，全部来自集成测试的 `fake-comfy/output/ComfyBatch-V2/`：
- `001-提示词_001_00001_.png`（900,008 字节）——PNG 签名后面接 90 万个 0 字节
- `abcd1234/001-探针1_00001_.png`（100 字节）——内容是 100 个 `x`

它们路径存在、也有记录引用，但永远渲染成裂图。缩略图生成器独立报出同样这 8 个失败，两边互相印证。

**3. 只显示前 60 张。**
`renderGrid()` 里硬编码 `const max=60; hit.slice(0,max)`，页脚只留一句「仅显示前 60 张」。7018 张里有 6958 张翻不到。

**4. 统计页数字在眼皮底下跳。**
`apply()` 每次筛选都调 `renderStats()`，而统计是全量聚合 + 画图；条件一变整页重绘，也没法对照改条件前后。

## 改动

### 缩略图缓存（新增 `tools/build_thumbs.py`）

- 每张图压到宽 420px 的 webp（quality 78，约 26KB，缩小约 85 倍），落在 `C:\Users\wyj\Desktop\_style_atlas_thumbs\t\<sha1前16>.webp`。
- 并行生成（12 进程），7018 张约 **58 秒**，合计 **138MB**。
- **网格只取缩略图，点开大图仍读原图** —— 清晰度不受影响。
- 幂等：目标文件比原图新就跳过，可随时重跑补新增的图；`--force` 全量重做。
- 落盘原子替换（先写 `.tmp` 再 `os.replace`），中断不会留半个文件。
- manifest 记录每个文件夹 / 批次的封面图（选该组体积最大的一张，`(-size, path)` 排序保证确定性），封面直接复用网格缩略图，不额外生成。
- 未被引用的缩略图只报告不删除（删文件不可逆，而它们占地很小）。

哈希是**路径的 sha1 前 16 位**：同一张图每次构建必须得到同一个名字，否则前端引用的名字和磁盘文件对不上。Python 端 `thumb_hash()` 与前端 `thumbSrc()` 必须一致。

### 主分类 / 次要维度

- `FACET_DEF` 拆成 `PRIMARY_DEF`（文件夹 / 批次·时间）与 `SECONDARY_DEF`（风格库 / 风格词条 / 技法 / LoRA / 底模 / 主题 / 方案）。
- 主分类渲染成**缩略式按钮**：一张封面图 + 短标签 + 张数。理由是这两维的值本身不表意——`c/E`、`7155c6f7` 光看名字不知道是什么，看一眼封面就认出来了。
- 文件夹标签**必须带父级前缀**。磁盘上有 22 组同名目录（`D/34393175` 与 `c/34393175`、`D/7155c6f7` 与 `c/7155c6f7` …），只显示末段会让两组按钮长得一模一样。超过 9 字符截断。
- 批次按钮带日期：数据里没有生成时间戳，用该批图片文件的 **mtime** 当代理（`D.run_time`），并按时间倒序排——最近的批次最常翻。`_UNNAMED` 显示为「未命名」并排在最后。
- 主分类默认显示 12 个，可「展开全部」（文件夹 185 个 / 批次 99 个），展开后限高滚动。

### 分页

`build_atlas.py` 已有分页骨架（`PER=__MAXTHUMB__`），本次把默认值统一为 **48**（`build_atlas.py` 与 `atlas_server.py` 的 `--max-thumb` 都是 48）。切筛选条件自动回第 1 页。

### 统计页点击才更新

- `apply()` 不再直接 `renderStats()`，改成 `markStatsDirty()`：顶部提示条变橙，写明「筛选条件已变化（现在命中 N 张）—— 下方数字仍是上次统计的结果」。
- 数字只在点「↻ 更新统计」时重算；进入统计页签本身算一次点击，会渲染一次。
- 自动刷新（`applyRemoteData`）也走标脏，不再把用户正在看的数字换掉。
- 顺带让统计页的排名行**真的可点**（页面本来就写着「点标签可直接跳转筛选」，但行上没有 `onclick`）。点一下加入筛选条件，数字仍要再点更新。

### 图片加载兜底改三级

原 `imgErr()` 只在 `/img` 和 `file:///` 两条通道间切换。现在：

1. 缩略图失败 → 换原图（缩略图是缓存，可能没生成；原图一定在磁盘上）；
2. 原图失败 → 换另一条取图通道；
3. 都失败 → 标灰**并把路径写进 `title`**，让「这张图打不开」变成一句能读的话。

### 剔除坏文件（`style_atlas.py`）

新增 `image_dimensions()` / `is_sane_image()`：**纯标准库**读文件头拿宽高，不解码（PNG/GIF/BMP/WebP/JPEG 五种头）。`build()` 在生成 `uid` 前过一遍，剔除读不出正数宽高的文件。

为什么不用 Pillow：启动器用的解释器未必装（注：本机实测 `.workbuddy/…/3.13.12` 其实**有** Pillow 12.3.0，早前记录已过时）。即便如此，纯标准库版本依赖更少、只读几十字节，仍然是更稳的选择。目标约 1.5 秒。

### 服务端 `/thumb` 路由

`/thumb?h=<16位hex>&s=t` 直接端出缩略图文件。哈希按 `^[0-9a-f]{16}$` 白名单校验——这个值会被拼进文件路径。非法 400、不存在 404。

### 消灭一份重复实现

`atlas_server.py` 原先自己抄了一份「数据装配 + 模板替换」，只替换 `__DATA__` / `__MAXTHUMB__` 两个占位符。本次新增 `__THUMBDIR__` / `__THUMB_OK__` 后，服务端那份会留下未替换的字面量，前端直接**整段 JS 语法错误、所有函数都不存在**。

改法：派生逻辑收到 `build_atlas.enrich()`，替换集中在 `build_atlas.render_html()`，命令行和服务端共用同一条路径。`render_html()` 的 docstring 里写明——新增占位符只改这一处。

### 路径分隔符混用（检查 URL 字符串时才发现）

`THUMBDIR` 从 Python 注入时是 Windows 反斜杠，拼出来的直开 URL 是：

```
file:///C:\Users\wyj\Desktop\_style_atlas_thumbs/t/8736db7e167e4f50.webp
```

`\` 和 `/` 混用。浏览器多半会容错，但这不是能靠猜的事——原图路径一直没这个问题，是因为数据里存的本来就是正斜杠（`C:/Users/wyj/Desktop/...`），两边不一致才暴露出来。

修法：`render_html()` 注入前 `replace("\\", "/")`，JS 侧再 `.replace(/\\/g,'/')` 兜一层。已逐条核对生成的 URL 指向真实文件、无反斜杠残留。

**教训**：新增一个拼接出来的 URL 时，把最终字符串打出来看一眼，别只看它"能用"。这次是顺手核对磁盘才发现的——只验证"页面能开、图能显示"的话，它会被浏览器的容错掩盖过去。

## 顺带修掉的两个统计错误

**1. `countIn()` 对字符串字段用了 `String.includes()`，变成子串匹配。**
`"c/E".includes("c")` 为真，于是统计页「文件夹 c」显示 **6282 张**（真实值 14），`c/1` 会把 `c/11`、`c/1x` 一并算进去。数组字段（libs/techs/styles）用 `includes` 判成员是对的，只有 `folder` 是字符串所以中招。改成按类型分支：数组用成员判断，字符串用全等。

**2. 覆盖率分母口径错。**
原先用 `S.catalog_available`（3946 = 整个风格库目录，含图鉴里一张图都没有的库），算出覆盖率 **5.22%**。改成只累计「图上真的出现过的 25 个风格库」登记的 1217 个词条，覆盖率 **16.9%**（1011 个没试过）。差三倍。

**3. 页头计数改成图库真实张数**（原写 `stats.resolved`=3796 条生成记录，比图库能翻的 7018 张少一半，看的人会以为图丢了）。

# 第二轮：使用反馈的三处修复（同日）

改版后收到三条反馈，逐条查因修复。

## 一、点开图片显示的不是点的那张

**根因是索引口径不一致，不是图片错配。** `openV(gi)` 传的是**全局序号**
（`gi=(PAGE-1)*PER+本页序号`），而 `renderGrid()` 把 `window._shown` 设成了**本页**
的 `list`（48 张）。第 1 页两者恰好重合所以看不出问题；从第 2 页起 `list[48]` 是
`undefined`，`sync()` 在 `im.path` 上抛 `TypeError`，大图就停在上一张上。

实测确认：第 2 页点第一张，`_shownLen=48`、传入序号 48、
`TypeError: Cannot read properties of undefined (reading 'path')`。

**修法**：`window._shown=hit`（整份筛选结果），序号口径就一致了。附带好处是大图里
按 ‹ › 能一路翻完整个筛选结果，不用关掉重开。同时给 `sync()` 加了越界分支——
越界时明确写出「序号越界（N / M）」，而不是抛异常后停在旧图上。
**后者才是这个 bug 藏这么久的原因**：它表现为「图对不上」，而不是任何错误。

## 二、统计「各维度分布」内容空白又占地方

两个独立原因叠在同一个区块：

1. **画布被拉伸**。`.grid2` 是两列 grid，默认会把同一行的盒子拉到等高。左边
   「文件夹分类」有 14 行需要 440px，右边「技法维度」的 Chart.js 画布只有 208px，
   于是底下空出 **232px**。
2. **共现恒为空**。`pairList()` 里只有「是 style 就用 `im.styles`，否则一律用
   `im.themes`」这一支，于是「风格库 × 风格库」去 `im.themes` 里找风格库名，
   永远找不到 —— 显示「无」，却照样占着一整块 337px 的高度。

**修法**：

- `.grid2` 加 `align-items:start`（盒子按内容高度，不拉伸），新增三列 `.grid3` 同样处理。
- **技法维度从 Chart.js 画布改成排行条列表**，和文件夹一致。三条理由：
  画布是固定宽高比会被拉伸；Chart.js 走 cdn.jsdelivr.net，断网时 `new Chart` 抛异常
  而它在 `renderStats` 里排在前面，**后面的文件夹/主题/共现全都不渲染**——一个图表
  挂掉带走整页；排行条还能点（加了 `onclick`），图表不能。
- 现在**整页没有外部依赖，断网可用**。`<script src=chart.js>` 已删除。
- `pairList()` 按 kind 取字段：`style→styles` / `theme→themes` / `library→libs`。
- 顺手把「批次 · 时间」也提成一列（主分类现在在统计页也有一席之地），
  批次行用「日期 + 短 id」——同一天常有好几批，只给日期几行长得一样。

## 三、标记页压缩文字 UI

实测改前整页 **4138px**，其中两段文字区（风格画像 786 + 配方反推 1641）占了一大半，
而配方里每张缩略图只有 52px —— 比例是反的。

**只动字号/间距/内边距，不动任何图片尺寸**：

| | 改前 | 改后 |
|---|---|---|
| 工具栏 | 2 条（55 + 56px） | **1 条**（夹切换 + 全部动作合并，统计文字挪进小节副标题） |
| 风格画像区 | 786px | **587px** |
| 配方反推区 | 1641px | **1095px** |
| 配方单条 | 205px | **104px**（三行文字并成一行内联） |
| 配方缩略图 | 52px | **52px（不变）** |
| 图片卡片 | 158px | **188px（变大）** |
| 整页 | 4138px | **3726px** |

图片不但没缩，反而从 158px 提到 188px 与图库对齐。56px 的配方缩略图也保持原样。

### 过程中自己引入又修掉的一个错

把标记页的图片网格从内联样式改成 `class="grid"` 时，忘了 CSS 里只有

# 第三轮：标记夹去重（同日）

## 现象

标记栏里出现 4 个都叫「默认」的夹：`42 / 0 / 42 / 0`。比对后确认
**两个 42 张的夹内容完全相同**（uid 逐一比对，交集 42、并集 42），两个是空的。
信息量等于 1 个夹。

## 成因：合并只认 id，不认名字，而两边 id 规则不同

| | 生成规则 | 形如 |
|---|---|---|
| 前端 `newSetId()` | `'s' + Date.now().toString(36) + 随机4位` | `smunrdmb4rvsc`（带字母） |
| 后端 `_new_set_id()` | `"s%d%04d"`（毫秒取模 + 随机） | `s7508233195682`（纯数字） |

同一个逻辑上的「默认」夹，在前端建和在服务端建会拿到**完全不同的 id**。而
`mkInit()` 的合并是「按 id 对齐，本地独有的就新增」，两个 id 对不上就变成两个夹。
之后两个夹先后都收到同一批标记，内容自然一模一样。空夹同理。

## 处理

**1. 数据清理** —— `tools/清理标记夹.py`（**新增，默认预演**，`--写入` 才落盘）：

- 先按「文件集合」分组，同内容的只留一个；
- 再按「名字」处理：空的一律丢，内容被同名非空夹完全包含的丢，
  **内容确实不同的同名夹保留**（那可能是用户有意分的两份）；
- 名字不重复的夹一律原样保留 —— 空夹也可能是建来准备收集的；
- 保留优先级：激活的 > 内容多的 > 备注多的；
- 被丢弃夹的 `note` 备注合并进保留者，不覆盖已有值；
- **写前自检**：去重后的标记数必须不变，一变就中止（`42 → 42` 才放行）。

执行结果：4 个夹 → 1 个（`s7508233195682`，42 张）。原文件备份为
`_marks.json.bak-20260930_160217`。

**2. 根因修复** —— `mkInit()` 的合并加一层**按名字兜底**：本地独有的夹，
若和某个同名夹内容重合（或它本身是空的，没有任何标记要保），就并进去，
不再新建；只有内容确实不同才另立一个。

这一层不是可选的：清理只动了 `_marks.json`，浏览器 localStorage 里那 4 个夹还在，
**下一次刷新就会按老逻辑重新长出重复**。加上兜底后实测 —— 刷新前 localStorage 是
4 个夹，刷新后自动收敛成 1 个，并把结果推回服务端。

## 验证
