# V2.27：图鉴「连接时间长」的性能归因与修复（2026-10-03）

## 现象

V2.26 把图鉴内嵌进 S 之后，切到「风格图鉴」模块要等一段时间才出图。

## 归因：先量，再猜

### 被数据否掉的两个猜测

| 猜测 | 实测 | 结论 |
|---|---|---|
| watch 每 20 秒的全盘扫描拖慢了服务 | **0.20 秒**（扫 31740 个文件） | 不是 |
| 重建期间服务响应退化 | 重建全程 `/api/data` 仍 60–116 ms，空闲基线 59–114 ms | 不是 |

第二项否掉的原因值得记：热点全在文件 IO 上，会释放 GIL，所以 HTTP 线程不受影响。

### 热路径本身很快

| 请求 | 耗时 | 体积 |
|---|---|---|
| `/api/version` | 1.2 ms | 225 B |
| `/?embed=1` | 46.8 ms | 6,781,293 B |
| `/api/data` | 62 ms | 6,667,510 B |

### 真凶：`style_atlas.build()` 独占 20.03 秒

占整次 rebuild 的 **97%**（enrich 0.37 s、render_html 0.08 s、写盘 0.02 s 都可忽略）。
cProfile 分解：

| 热点 | 耗时 | 量级 |
|---|---|---|
| `re.search` —— 技法维度判定（`tech_of`） | 7.22 s | **418 万次** |
| `open()` —— 读 PNG 文件头 | 6.38 s | 13,457 次 |
| `styles_by_prompt_text` | 1.68 s | 892 次 |
| manifest + JSON 读取 | ~3.4 s | |

两个白做的动作：**每张图被 open 两次**（一次判正常图片、一次读内嵌元数据），
以及 `tech_of` 的输入高度重复（风格库那 3946 条 prompt 被反复算了一万多遍）。

**而 build 的结果没有任何持久缓存** —— 每次 S 启动、每次新图落盘都从头算。

### 为什么现在才暴露

20 秒的构建在「独立图鉴」时代是合理的：偶尔双击一次，等一次就好。内嵌之后重建
频率变成「每次 S 启动 + 每次出新图」，偶发等待变成常态等待 —— **是 V2.26 的内嵌
把这个既有问题放大出来的**。

## 改动

### 1. 一张图只读一次盘（`style_atlas.py`）

新增 `png_prompt_text(path)`：PNG 里那段执行图原文。原先 `styles_from_png` 和
`png_positive_text` 各读一次同一个文件，现在共用一份结果。`png_positive_text`
（解析执行图 JSON 找最长 CLIPTextEncode 正文）的结果也一并缓存。

### 2. 派生结果持久缓存（`style_atlas.py`）

`_derive_cache.json`，两个 bucket：

* `files` —— key 是 **用途标签 + 路径 + (mtime_ns, size)**：
  尺寸判定、执行图原文、正面正文、风格归因。
* `text` —— key 是正文的内容哈希：`tech_of` 的结果。

失效靠 `(mtime_ns, size)`：图被重新生成，mtime 就变，账自动作废 ——
不需要谁记得清缓存。风格归因额外带 `_STYLE_SIG`（风格库内容指纹），
词条或 prompt 改了结果就重算。

build 收尾 `cache_flush()` 一次落盘；`rebuild` 的 `finally` 里也补了一次 ——
构建中途失败时，已经算出来的部分不该白费。

### 3. 启动预载（`atlas_server.py`）

rebuild 成功后把整份 data 落盘 `_data_cache.json`；启动时（`bootstrap="background"`）
先 `_preload()` 把它端上来，再在后台重建核实。

* 数据在、页面不在（换数据目录 / 首次升级）→ 现场渲染一份（0.08 秒）；
* 内存里已有数据时不覆盖；
* 缓存读坏 → 当作没有，安静地走完整重建。

这一条打的是体感：用户点开图鉴的瞬间就有图，而不是先读一句「正在建立索引」。

## 过程中自己引入又修掉的一个 bug

加完缓存后，图片数从 **7315 掉到 3976**。

原因：`_fkey(path)` 被四个查询共用，`image_dimensions` 和 `png_prompt_text` 撞了
同一个 key。前者读到了后者存下的 JSON 字符串，拿前两个字符当宽高，
`is_sane_image` 判失败 → **三千多张图被静默剔除**，日志一声不吭。

两次构建的结果「逐张一致」，所以只做一致性检查是发现不了的 —— 是**对比基线
（7315）**才看出来。

修法：`_fkey(path, tag)` 每个用途独立命名空间；`_CACHE_SCHEMA` 升到 2，旧格式
一律作废。

新增 `tests/test_atlas_cache.py` 专门盯这一类：**同一个文件问不同的事，答案不许
互相覆盖**，四种查询轮流问两遍、正反两种顺序都覆盖。

顺带修掉一个脆弱点：`image_dimensions` 原来在文件不可读时直接抛
`FileNotFoundError`，生产路径靠 `is_sane_image` 的 try 兜着。扫盘期间用户删图是
常态，改成返回 `None`。

## 被实测否掉的方案

**把每个技法维度的多条正则合并成一条 `(?:a|b|c)`** —— 看起来能把 418 万次
`re.search` 收成十万量级，实测**反而慢 11%**（1500 条真实 prompt，重复 4 轮取最快：
0.521 s → 0.577 s）。

原因：单条 pattern 能吃到字面量前缀的快扫，每维度十几条分支塞进大交替后这个优化
就失效了。结论写进了 `_COMP` 处的注释，避免以后有人再试第二次。

## 验证

### 构建耗时（同一个数据目录，冷/热各一次）

| 场景 | 耗时 | 图片数 |
|---|---|---|
| 优化前 | 20.03 s | 7315 |
| 冷构建（删掉缓存） | **14.14 s** | 7315 |
| 热构建（有缓存） | **4.30 s** | 7315 |

**加速 3.3 倍**。更强的证据是 **`build_id` 前后一致（`913c0b565d`）** ——
它是内容指纹，没变就说明输出数据一字未动，缓存没有改变任何结果。

### 冻结态端到端（`build/dist-v227/S.exe`，这才是用户视角）

「端口活」= 服务能应答；「页面可渲染」= `/api/data` 首次返回非空；
「后台重建完」= `building=false`。**三个时刻要分开算** —— 预载之后
「后台重建完」比「页面可渲染」晚 5 秒多，把它算进用户等待就会得出
「预载没用」的错误结论（第一版判据就是这么错的）。

| 场景 | 端口活 | 页面可渲染 | 后台重建完 |
|---|---|---|---|
| 无预载（把 `_data_cache.json` 改名做对照） | 2.90 s | **8.16 s** | 8.11 s |
| 有预载 | 2.86 s | **2.90 s** | 8.12 s |
| 部署版（桌面 `S.exe`） | 3.27 s | **3.17 s** | 9.95 s |

- 预载省下 **5.26 秒**，页面在端口一活的瞬间就能渲染。
- 全程 `images=7315`、`build_id=913c0b565d`，与优化前同一份内容指纹。
- 8790 与 8793 同为**同一 PID**（24676）；标记夹「默认 43 张」完好（`dropped=0`）。
- 宿主日志佐证：有预载那次紧跟一句「已载入上次索引（7315 张 …）」，无预载那次直接「构建索引 …」。

## 遗留

- **缓存没有 GC**。key 是「路径 + 戳」，同一张图重新生成只是换一个 key，老 key 会
  留下。实测 7315 张的账：`_derive_cache.json` **31.8 MB**（大头是逐图的提示词正文，
  比早先估的 4 MB 大得多）、`_data_cache.json` 6.67 MB。孤儿增速是「被重新生成过的
  图的张数」，短期无碍；真涨起来要加按目录回收的口子。
- **首次构建仍是 8～14 秒**（预载/缓存都为空时）。要再压只能继续拆：`_manifest` 与
  `styles_by_prompt_text` 合计约 3.4 秒尚无缓存，`_glob_reports` 的目录遍历也还在
  每轮重跑。目前没做，因为用户日常路径（第二次起）已经只付 ~3 秒，图鉴是秒开的。
- **页面 6.78 MB 仍是每次切回模块就重新加载**（`suspendAtlas` 把 iframe 设回
  `about:blank`）。本地传输只要 47 ms，剩下的开销在浏览器解析那 6.67 MB 内嵌 JSON
  上。要再省，得把数据从页面里拆出去走 `/api/data` 按需拉 —— 那是另一轮改动。
