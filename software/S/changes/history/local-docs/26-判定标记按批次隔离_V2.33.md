# 26 - 判定标记按批次隔离（V2.33）

日期：2026-10-03
上一版：V2.32（`docs/25-对比页直接标记淘汰保留_V2.32.md`）

## 起点：一个问句

> 「我在 10 月 2 号的批次中进行来了标记，之后我关闭进程，标记会保存吗？像收藏一样进行保存」
>
> 「我现需要的实时更新在最新的软件版本中，老旧的版本不要占据空间。
> 就像我在 92 张的批次中，选中了一些，不希望和之前的混在一起」

拆成三件事：

1. **标记会不会丢** —— 关进程后还留着吗
2. **最新版要落地** —— 桌面 S.exe 得是真的新版，历史构建产物别占空间
3. **批次不能混** —— 92 张那批的标记要和之前的隔开

第 1 件是**已经成立的**：标记走 `_marks.json` 落盘，`.tmp → os.replace()` 原子写，
关进程不丢。用户 10-02 那批 43 张确实还在盘上。

第 3 件才是真需求，也是本版做的东西。

## 核心矛盾

V2.32 的判定夹只有两个 id：`verdict-reject` / `verdict-keep`。
**所有批次的标记挤在同一个夹里**。用户标 92 张那批时，之前批次的图还挂在同一个夹里，
看起来就是「混在一起」。

## 设计：夹 id 带批次后缀

夹 id 从 `verdict-keep` 变成 `verdict-keep@<batch>`，夹名 `保留·<batch>`。
批次号从哪来？uid 的结构是 `<绝对路径>#<批次>#<序号>`：

```js
function batchOf(it){
  const u=String((it&&it.uid)||'');
  const parts=u.split('#');
  if(parts.length>=3){
    const b=parts[parts.length-2];
    if(b&&b!=='None'&&b!=='_UNNAMED'&&b!=='_unnamed') return b;
    return 'x';        // 没有批次的，统一归 x
  }
  return 'x';
}
```

## 三个必须处理的边角

### 1. 老夹继承（`inheritSetId`）

**这是真机验证逼出来的。** 我在真数据上跑验证，断言「不应出现无后缀全局夹」失败了——
基线里有个 `('保留', 15)`。

查证：那是用户 V2.32 标的 `verdict-keep` 老夹，**15 张全部来自批次 `926266f5`**。
如果不处理，升级后他再标这个批次的图，就会**新建 `verdict-keep@926266f5`，
而同批的 15 张还在老夹里** —— 同一批图被劈成两个夹，比不隔离还乱。

修法：同批次存在无后缀老夹时，**继续写老夹**。

```js
function inheritSetId(kind,batch){
  const base=verdictSetIds(kind);
  if(!batch||batch==='x') return base+'@x';
  const legacy=(MARK_SETS||[]).find(s=>s.id===base);
  if(!legacy) return base+'@'+batch;
  const hit=(legacy.paths||[]).some(u=>batchOf({uid:u})===batch);
  return hit?base:base+'@'+batch;     // 老夹里有同批图 → 复用；否则新建
}
```

这正是「先自己查，再动手」救回来的地方：**如果只看测试绿灯就部署，
这个分裂问题会直接落在用户数据上。**

### 2. `_UNNAMED` 是占位，不是批次

用户 43 张里 **26 张的 uid 没有批次号**（早期没走批次的图），
值分别是 `None` / `_UNNAMED`。它们必须归到统一的 `x` 夹，
否则会凭空多出 `淘汰·_UNNAMED` 这种夹。

这个是真缺陷 —— 前端逻辑测试第一个版本就抓出来了（`batchOf` 初版只排除了 `'None'`）。

### 3. 空夹回收 + 老夹护栏

派生夹空掉就该删，否则夹列表越堆越长。但**无后缀老夹是用户的历史数据，绝不能删**。

护栏放在**服务端**，不依赖前端自觉：

```python
if bool(op.get("drop")):
    if "@" not in sid:
        continue          # 老夹不可删，静默跳过（不是错误）
    ...
```

前端 `clearVerdicts` 也做了双保险：只回收带 `@` 的派生空夹。

## 存量数据：拆不拆，问用户

真数据现状：

| 夹 | 张数 | 批次分布 |
|---|---|---|
| 默认 `s7508233195682` | 43 | `x` 26 张 + 13 个批次共 17 张（每批 1–3 张） |
| 保留 `verdict-keep` | 15 | `926266f5` 全部 15 张 |

发现问题：**「默认」是用户手工建的夹**（id 是 `s7508…` 不是判定夹），
里面 26 张根本没有批次号，硬拆会碎成 13 个 1–3 张的夹。

摆清代价让用户选，用户选了「**只拆判定夹，默认不动**」。

迁移脚本 `run/migrate_verdict_batch.py`：

- 只处理 id 属于 `verdict-reject` / `verdict-keep` 的夹，手工夹原样保留
- 干跑模式（默认）+ `--apply` 落盘
- 落盘前自动备份；原子写
- **自检硬断言**：总数一致、uid 集合一致、手工夹逐条未改动

结果：`保留` → `保留·926266f5`，默认 43 张原样，夹数 2 → 2。

## 环境坑（本版又踩到的）

- **图鉴服务在 8793，不是 8790。** 探 8790 的 `/api/version` 返回
  `{"ok":false,"error":"未找到接口"}`，白等 150 秒。8790 是生图工作台。
- **打包 exit=1 但日志无 Error，是安全策略拦的**：
  `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":259,"threshold":50}`。
  `--noconfirm` 要清 259 个文件超阈值。**指纹没变说明产物是旧的**，
  险些用旧包部署。改用新目录 `dist-v233b` / `work-v233b`。
- 判定夹要小心「**验证别碰用户真数据**」：真机验证里我想造无后缀老夹来验护栏，
  但那会在用户数据里留一个删不掉的垃圾夹。改成走单元测试验，不碰真数据。
