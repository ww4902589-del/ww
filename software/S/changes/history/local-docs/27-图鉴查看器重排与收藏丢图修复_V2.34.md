## 一、收藏夹里的图不见了，但数量没变

### 1. 症状层事实

用户说的是「收藏夹 1」。`1` 就是 `verdict-keep@926266f5`（V2.33 引入的判定夹，
显示名 `1`，源目录里原本叫「保留·926266f5」）。数字是从 `软件s修改。/S本地资源核查.json`
读到的（该文件是上一轮只读核查留下的现场记录，`checked_at=2026-10-06T12:11:54Z`）：

```
favorites.stored_references     74      ← 磁盘 _marks.json 里真实存着 74 条
favorites.api_references        44      ← /api/marks 只返回 44 条
favorites.api_dropped           30      ← 少了 30 条，接口自己知道
favorites.sets[0]  默认     stored 55 / returned 40
favorites.relocation_candidates 30     ← 逐条给出了同名候选
```

「数量没变」和「图不见了」能同时成立，是因为**前端数的是「记录条数」，用户看的是
「能显示出来的图」**。记录还在、图没了 —— 或者更糟：记录被删了、数字由别处补齐。

### 2. 真因：静默过滤 + 整体覆盖写回

两层，各自都"看起来正常"：

**第一层（后端）**：`tools/atlas_server.py` 的 `/api/marks` 会先过一道
「文件还在不在原路径上」的过滤，把指向不存在文件的记录**从返回值里剔掉**，
而且**不告诉前端剔了多少**。于是接口返回 44 条，前端以为这就是全部。

**第二层（前端拿它当权威）**：图鉴页的写协议是「前端持有的全量 `sets` 整体覆盖服务端」。
只要前端手里那份比服务端少，一次 `switchSet` 触发的 `mkPersist()` 就会
**把少掉的那些从磁盘上真删掉**。

两层一叠加，就是一条静默数据销毁链：

```
磁盘 74 条 → /api/marks 静默返回 44 条 → 前端合并后只认 44 条
          → 下一次写回把磁盘覆盖成 44 条 → 30 条永久消失，且没有任何提示
```

**实测发生过两次**，这是本轮最硬的证据：

| 时刻 | `_marks.json` | 默认 | 1 |
|---|---|---|---|
| 核查快照（`_verify/atlas/_marks.json`） | 10,838 B | 55 | 40 |
| **还原前**（`_marks.json.bak_restore_20261006_205243`） | **7,502 B** | **40** | **25** |
| 还原后（`_marks.json.bak_relocate_20261006_205247`） | 10,845 B | 55 | 40 |

7,502 → 10,845 = **补回 30 条**。而且：

```
丢失的 30 条 100% 是死引用（文件真的不在记录路径上）；活引用 0 条丢失。
```

这一条把归因钉死了：如果用户是手动取消收藏，丢的应该是活引用；只丢死引用，
只能是那道「过滤掉死引用」的代码干的。

### 3. 修法

**后端 —— 不再有静默过滤**（`tools/atlas_server.py`）：

```python
dead = []
for s in m["sets"]:
    for p in (s.get("paths") or []):
        if not uid_alive(p):
            dead.append(p)
m["dead"] = dead
m["dropped"] = len(dead)      # 兼容旧字段名，客户端不升级也不会 KeyError
```

**记录原样全返回，另外把「哪些是死的」单独报出来。** 前端因此第一次有了
「我拿到的比存的少」这个信息。

**前端 —— 把「可显示」和「待定位」拆开**（`tools/build_atlas.py`）：

```js
function resolveSet(set){ ... }   // → {live, dead}，dead 原样保留，绝不丢
function setImages(set){ return resolveSet(set).live; }   // 语义不变：只给能显示的
```

* 夹角标写 `live + dead`（`40+15`），而不是只写 `40`；
* 夹标签写完整三数：`可显示 40 张 · 记录 55 条 · 待定位 15 条`；
* 新增**待定位区** `pendingSectionHTML()`：每条列出原路径、同名候选的
  「归位到 …」按钮、以及「移除记录」；
* `updateStampMarks()` 区分「重复登记」与「待定位」 —— 旧代码用「重复登记」
  这个提示盖掉了真实的数据丢失，是这次查不出来的一个帮凶。

**这就是「不损伤现有信息」的落地**：不确定的记录不再是「静默消失」，
而是「显式显示为待定位 + 给用户一个归位按钮」。

### 4. 数据抢救（真数据，可回滚）

三步，每一步都自动备份，都是「干跑 → 核对 → `--apply`」：

| 脚本 | 作用 | 规则 | 备份 |
|---|---|---|---|
| `run/restore_marks_from_snapshot.py` | 把被前端写回删掉的记录补回来 | **只补**「快照里有、现在没有、且当前确实指向一个不存在的文件」的 | `_marks.json.bak_restore_20261006_205243` |
| `run/migrate_marks_relocate.py` | 按核查 json 的 30 条候选归位 | 候选必须**现存**且在索引里（把「建议」当**断言复核**，不是照抄） | `_marks.json.bak_relocate_20261006_205247` |
| `run/normalize_marks_uid.py` | 消掉 uid 漂移 | 只改 `#批次#序号` 后缀，路径一字不动 | `_marks.json.bak_normalize_20261006_205744` |

实测输出：

```

[恢复] 夹「1」：补回 15 条待定位记录
```

**最终不变量**（`run/_final_marks_audit.mjs`，直接读 `_marks.json` + 渲染出的索引）：

## 二、多次点「下一张」，显示区不断上移且无法恢复

### 1. 真因：`flex column + center` 的溢出上侧落进了「不可达区」

旧查看器：

```css
#viewer{position:fixed;inset:0;display:flex;flex-direction:column;
        align-items:center;justify-content:center}   /* 没有 overflow */
#vimg{max-height:82vh}                                /* 百分比是「视口」的，不是「视口减去文字」的 */
```

`justify-content:center` 在**内容高于容器**时，会把溢出**均分到上下两侧**。
下侧那截有 `scrollHeight` 兜着，上侧那截直接落在 `scrollTop` 能到达的最上沿之外 ——
**没有任何滚动条能到那里**。再叠上 `#vimg` 用 `82vh` 这种「不看上下文的高度」，
内容几乎必然溢出；而每切一张图，图片高度在变、信息块长短也在变，
于是整列重心**每次切图都在动**，看起来就是「显示区不断上移」。

实测复现（旧版，1260×640）：`<body>` 的 `scrollHeight` 约 1268px，是视口的两倍。

### 2. 修法：把「尺寸只由视口决定」的部分和「内容会变长」的部分切开

```css
#viewer{position:fixed;inset:0;display:flex;flex-direction:row;
        align-items:stretch;gap:18px;padding:22px 24px;overflow:hidden}
.vstage{flex:1 1 auto;min-width:0;min-height:0;             /* 舞台尺寸只由视口决定 */
        display:flex;align-items:center;justify-content:center}
#vimg{max-width:100%;max-height:100%}                        /* 相对舞台，不是视口 */
.vside{flex:0 0 330px;max-height:100%;overflow-y:auto}       /* 会变长的那部分自己滚 */
```

要点三条：

1. **舞台 `.vstage` 的尺寸只由视口决定**，于是它的矩形在切图之间是**常量**
   —— 验收器直接拿这个当判据（`stageRects` 必须只有一个值）；
2. **`#vimg` 的 `max-height:100%` 是相对舞台**，25% 的溢出不会再出现；
3. **信息块移到右侧独立滚动**，它再长也不会推图片。

窄屏（`≤900px`）另写一套：改回上下排，并且**明确 `justify-content:flex-start`**
—— 居中 + 溢出这个坑，在窄屏同样会犯。

另外 `sync()` 里把 `#viewer` 和 `#vside` 的 `scrollTop` 都归零，
保证连续切图不会累积出偏移。

## 三、详情查看时，图片信息没在旁侧

上一版查看器里**根本没有信息栏**：打开大图只有一张图和左右箭头，文件名、目录、
批次、尺寸一概看不到。所以这不是「位置不对」，是「不存在」。

新增右侧 `.vside` 信息栏（`viewerInfoHTML()`），六行：

```
文件名 / 所在文件夹 / 批次 / 序号 / 尺寸 / 大小
```

其中**「尺寸」由 `imgOk()` 在图解码完成后回填真实像素**（`naturalWidth × naturalHeight`），
所以它是等大图解码后的真值（实测 `1944 × 1088`），不是从 `data` 里读的缓存值。
`sync()` 里给它一个 `—` 占位，解码完成后替换。

验收器同时钉两条：**字段表渲得出**（6 行）且在**图片右侧**
（`beside:true`，`imgRight:994 < sideLeft:1012`）。

## 四、图片重命名

### 能力

| 层 | 实现 |
|---|---|
| 前端入口 | 查看器底部 `✎ 重命名`；网格卡片 `.acts` 里也有一个 `✎`（不用先点开大图） |
| 前端流程 | `renameCurrent()` / `renameAt(i)` → `prompt` → `renameImage(im, oldName)` → `applyRename(im, j)` |
| 后端 | `POST /api/rename` → `Handler._rename_image()` |
| 引用搬迁 | `Handler._remap_refs(old_path, new_uid)`：**收藏 + 评级**一起搬 |

### 改名必须同步搬引用 —— 这是这个功能真正的难点

uid 是 `<绝对路径>#<批次>#<序号>`，**收藏和评级都是以 uid 为键**。只改文件名不搬引用
＝ 用户眼里的「收藏又丢了一张」。所以改名是四件事一起做：

1. 磁盘上原目录内改名；
2. `_state["data"]` 里的 `path` / `uid` / `name` 跟着改；
3. `_marks.json` 里所有引用该路径的记录搬到新 uid（**同一夹内去重**）；
4. `_grades.json` 的评级键跟着搬。

前端侧同步搬 `D.images`、`SETS.paths`、`UG` 并把索引缓存 `_IX=null` 失效。

### 安全与边界（每条都有测试钉着）

| 规则 | 理由 |
|---|---|
| 只接受本机来源（`_local_origin_ok()`） | 有 `Origin` 且 host 不是 `127.0.0.1`/`localhost`/`::1` → 403；`null`/`file://` → 403。**防止任意网页通过 CSRF 改本机文件名** |
| 禁 `\ / : * ? " < > | & '` | 路径分隔符会逃出原目录；引号会破坏前端的 HTML 属性拼接 |
| **后缀不可改** | 改了后缀文件名就不在图片扫描范围内了 = 图消失。无后缀则沿用 |
| 拒绝覆盖已存在的文件 | 改名不能变成静默删除 |
| 仅大小写不同走中转名 | Windows 大小写不敏感，直接改会失败 |
| `th`（缩略图哈希）**故意不变** | 缩略图是内容寻址的，内容没变就不该重新生成 |
| 同名 no-op | 改成一个和现在一样的名字，直接返回成功，不落盘 |

## 五、顺带修的两个（破图状态残留 / 缩略图 404）

### 1. 破图状态残留（`fb` / `opacity:.22`）

核查 json 里三条现成事实：

```
/viewer/failure_opacity                  = 0.22
/viewer/switch_does_not_reset_opacity    = True
/viewer/clears_fbDone_but_actual_error_state_is_fb = True
```

前端 `imgErr` 的三级兜底链（缩略图 → 原图 → 另一通道 → `fb=3` + `opacity:.22`）
把状态挂在 `fb` / `fbDone` / `opacity` 上。而旧 `sync()` **清的是 `fbDone`**，
真正的错误状态是 `fb` —— 于是切图时那个 `opacity:.22` 的灰图**一直留着**。

修法：`sync()` 里全面复位（`delete dataset.fb` / `delete dataset.fbDone` /
`opacity=''` / 清 `title`），**并且**新增 `imgOk()`：
**任何一次成功加载都复原状态**。这是硬兜底 —— 不依赖调用方记得清。

### 2. 缩略图 404（4,725 张）

`missing_grid_thumbnails = 4725`。原因：前端请求 `/thumb?h=<sha1>` 时**没带原图路径**，
服务端在缩略图缺失时没有重建的线索，只能 404。

修法：

* 前端 `thumbUrl(h, path, size)` 带 `p`：
  `/thumb?h=<h>&s=<s>&p=<encodeURIComponent(path)>`
* 服务端 `/thumb` 用 `p` **现场补建**（420px LANCZOS webp q78），
  加 `threading.Semaphore(3)` 并发闸门 —— 页面一开就是几百个缩略图请求，
  不限并发会把磁盘打满。

## 六、附带修掉的另外两个（部署到真机才暴露）

这两个不属于用户报的四件事，但**不修的话这一轮等于没做** ——
用户升级完看到的还是旧界面，收藏还是乱的。

### 6.1 升级后服务端端出旧模板渲染的页面

**症状**：新 exe 部署完，`/api/ping` 是 2.34、`/api/rename` 也在，但 `GET /`
回来的页面里**没有 `.vstage`** —— 是旧模板渲染的那份。用户会以为改动没生效。

**真因**：`风格图鉴.html` 是一份**派生文件**，落在数据目录里，`GET /` 直接端给浏览器。
旧实现只判「文件在不在」：

```python
p = os.path.join(DATA_DIR, "风格图鉴.html")
if not os.path.isfile(p):     # ← 只看存在性
    ...渲染一份...
html = open(p, encoding="utf-8").read()   # ← 在就直接端出去
```

换了 exe（里面是新的 `build_atlas.py`）之后，磁盘上那份旧页面依然存在 ——
实测那份是**几分钟前还在跑的旧版 exe 在自动重建时写下的**（mtime 21:02），
于是新服务端原封不动把它端给了浏览器。

这正是 V2.31 修过的 `folder_rule` 问题，但**管的是模板而不是派生列**。
V2.31 给「数据缓存」加了版本戳，却没有给「页面产物」加 —— 同类漏洞漏了一半。

**修法**：`build_atlas.RENDER_RULE` + 页面里的 `<meta name="atlas-render" content="N">`，
服务端只读开头 2KB 核版本，不匹配就重渲。

```python
# build_atlas.py
RENDER_RULE = 3          # 改了模板 / CSS / 前端 JS 就 +1
RENDER_META = "atlas-render"
# 渲染时写进 <head>：<meta name="atlas-render" content="__RENDER_RULE__">

def page_render_rule(path):     # 只读开头 2KB，页面 6~7MB 不必全文读
    ...
```

三处路径都要判，缺一处就等于没修：

| 位置 | 行为 |
|---|---|
| `_preload()` | 页面过期 → 重渲（升级后第一次启动就修好） |
| `GET /` | 页面过期 → **现场重渲**（数据在手 0.08 秒），没数据才退等待页 |
| `rebuild()` | 走同一个 `_write_page()`，保证产物一定带新版本戳 |

抽 `_write_page(data, max_thumb, page)` 的另一个理由：渲染原本散在三处，
**早晚有一份忘了带 `RENDER_RULE`，于是那份产物永远「过期」**。

实测（第三次部署）：

```
部署前 磁盘页面：7,086,157 B  render_rule=None  → 过期（旧模板）
部署后 / 页面  ：render_rule=2  磁盘：render_rule=2  → 已重渲
```

### 6.2 旧标签页把陈旧 uid 并回收藏（数据回潮）

**症状**：迁移把收藏清理到干净的 46 / 36 之后，几分钟后变成 **63 / 51**，
并冒出 **30 条死引用**。`+32` 这个数字很可疑。

**定位**：`+32 = 30 条死引用 + 2 条 uid 漂移` —— 正好是本次迁移**改动过的那 32 条**。
也就是「迁移前的那份数据」被原样送了回来。

**真因**：图鉴页的写协议是「前端整体覆盖 sets」，而前端手里那份是它的
`localStorage` 副本。`mkInit()` 里有一句**无条件并集**：

```js
SETS.forEach(ls=>{
  if(byId[ls.id]){ ls.paths.forEach(u=>byId[ls.id].paths.push(u)); return; }   // ← 本地独有的一律并进去
  ...
```

一个**升级前就打开着的旧标签页**，本地那份还是迁移前的 uid。它和服务端并集后
把旧 uid 写了回去 —— 46∪55 = 63、36∪40 = 51，与实测完全吻合。

**这不是数据丢失**（只增不减，且前端会如实显示成「待定位」），
但会让用户刚被修好的收藏又冒出 30 条待定位，体验上等于没修。

**修法**：让「同一个文件」在两边算出**同一个 uid**，并集就变幂等。

```js
function canonUid(u){ const im=findImage(u); return im?im.uid:u; }
function canonSets(list){ /* 逐条规范 + 同一夹内按规范 uid 去重 */ }
```

* `applyRemoteData()` 里调一次：新数据到达 = 索引变了 = 该对齐了，变了就 `mkPersist()`；
* `mkInit()` 的并集之后也调一次（数据已经到了的话）。

两条纪律：

1. **文件确实不在索引里时原样保留** —— 那是「待定位」，不能趁规范化抹掉；
2. **已经规整过就返回同一个数组引用** —— 否则每轮 `applyRemoteData` 都判成
   「变了」，页面每次刷新都白白 POST 一次 `/api/marks`。

数据清理：重新跑一次 `migrate_marks_relocate.py --apply` + `normalize_marks_uid.py --apply`
（旧 uid 归位后与已有的新 uid 重复 → 同夹去重），回到 **46 / 36**。

## 十一、本轮踩的坑（留档，下次会再撞上）

### 11.1 本机 HTTP 检查不能用 `urllib` —— 代理会把它变成 502

这个 shell 里带着 `http_proxy=http://127.0.0.1:57839`。`urllib.request.urlopen`
**尊重这个变量**，于是对 `http://127.0.0.1:8793/` 的请求被送到代理，回来一个
`502 Bad Gateway` —— 看起来像图鉴服务挂了，其实它好好的。

`http.client.HTTPConnection` 直连 socket，不走代理。**检查本机服务一律用它。**

这一条差点把结论带偏：我一度以为「部署后服务端在返回 502」，
而真相是**验证手段**有问题。区分方法很简单 —— 拿原始 socket 发一次
`GET / HTTP/1.1`，看回来的到底是 502 还是真响应。

### 11.2 沙箱在每次工具调用结束时清掉我起的进程

`subprocess.Popen`、`os.startfile` 都一样：把 S.exe 起来，当次调用一结束它就没了。
所以「启动 → 等待 → 测量」必须压进**同一次调用**（`run/_probe_deployed.py` 就是为这个写的）。

用户自己双击起来的进程不受影响 —— 这也说明这是沙箱的作用域问题，不是 S 的问题。

### 11.3 用脚本批量改代码时，不要在遍历过程中改列表

这次真改坏过 `tools/atlas_server.py`：

```python
hits = [i for i, l in enumerate(lines) if l == target]   # [905, 935, 956]
for i in hits:                                            # ← 每次替换都让后面的下标错位
    lines[i:i+1] = [...]
```

结果第 2、3 次替换打偏，**把两个 `return self._send(...)` 错误分支覆盖掉了**。
好在两件事救回来：

1. `py_compile` 立刻报了 `IndentationError`，没有静默带病继续；
2. 还原不是靠猜 —— 从**上一版 exe**（`build/dist-v233b/S.exe`）的 PYZ 里把
   `atlas_server` 的 code object 挖出来，`dis` 反汇编拿到原文：
   `/compare` 是 `500 + "compare_live.html 缺失"`，
   `/compare237` 是 **404** + `"对比审图台源文件不存在：" + p`。
   然后用**常量集合比对**证明还原无误：

```
旧 do_GET 字符串常量 62 个 / 新 67 个
--- 新增 --- +'RENDER_RULE'  +'max_thumb'  +'[图鉴] 首页命中过期页面，已现场重渲'
             +'[图鉴] 首页重渲失败：'  +'dead'
--- 丢失 --- （空）
```

**「丢失为空」才是证据。** 只说「我修好了」不算 —— 除非能证明没丢东西。

### 11.4 别把「验证脚本自己的错」当成产品缺陷

本轮验证器自己出了两次错，都长得像产品坏了：

| 现象 | 真因 |
|---|---|
| `/api/ping` 返回空体 → `JSONDecodeError` | 拿**图鉴端口 8793** 去 ping，而 `/api/ping` 只在主控 8790 上 |
| `GET /` 返回 502 | `urllib` 走了代理（见 11.1） |
| 「页面缺少 `.vstage`」 | 这条是**真的**，成了 6.1 那个缺陷的发现路径 |

处理办法：**错误信息里带上「我在请求什么」**。
`_json(text, where)` 现在会把原文前 200 字和请求目标一起打出来，
所以下一次再出这种事，一眼就能分清是谁的错。

### 11.5 测试污染全局状态，回旋镖打到别的模块

新增的 `StalePageNotServedTests` 把 `atlas_server._state["building"]` 置成了 `True`
但**只把 `data` 还了回去**。于是下游 `test_atlas_host.test_rebuild_writes_the_cache`
里的 `rebuild()` 撞上开头那句

```python
if _state["building"]: return False, _state["version"], 0.0
```

直接短路返回 `False`，一个看着毫不相干的测试挂了。
而且 `run_tests.py` 的模块顺序不同，**全量跑是绿的** —— 只有按特定顺序跑才复现。

修法不是在测试里补一句 `_state["data"]=None`，而是**入口整份快照、退出整份还原**：

```python
def snapshot_state(case):
    with S._state_lock:
        saved = dict(S._state)
    case.addCleanup(lambda: S._state.update(saved))
```

**只还自己动过的那几个键，迟早漏一个。**
（另附：全量绿 + 聚焦红 → 先怀疑模块间共享状态，再怀疑产品。）
