# S / ComfyBatch V2.14 架构说明

## 一、为什么要有新的模块划分

V2.13 把工作流编译、错误处理、HTTP 访问全部塞在 `comfybatch_v2_core.py` 里，结果是：

- 工作流编译依赖“按位置猜参数”，无法独立测试，也无法对外解释“哪个值写到了哪个参数”；
- HTTP 失败时正文被丢掉，错误处理没有可分类的输入；
- 测试只能把假 ComfyUI 内嵌在测试方法里，无法复用，于是关键路径（`UltimateSDUpscale`）
  完全没有覆盖。

V2.14 把这三件事各自拆成有明确入口的模块，并让它们之间只通过数据结构通信。

```
                 ┌──────────────────────────────┐
                 │  comfybatch_v2_app.py        │  进程入口 / HTTP 路由 / 持久化
                 │  Application · Handler       │  预设·LoRA档案·审核库·schema缓存
                 └───────┬──────────────┬───────┘
                         │              │
        ┌────────────────▼───┐   ┌──────▼──────────────────┐
        │ comfybatch_v2_core │   │ ResultReviewStore       │
        │ PromptCompiler     │   │ （同文件，按运行保存）    │
        │ Krea2WorkflowAdapter│  └─────────────────────────┘
        │ BatchRunner        │
        │ ResourceInventory  │
        └───┬────────────┬───┘
            │            │
   ┌────────▼──────┐  ┌──▼──────────────────────┐
   │ nodeschema    │  │ gateway                 │
   │ 模式注册       │  │ ComfyGateway 协议        │
   │ 按名绑定       │  │ ProductionGateway（真实） │
   │ 转换器注册表   │  │ FakeComfyGateway（内存）  │
   │ 提交图审计     │  └──┬──────────────────────┘
   └───────┬───────┘     │
           │             │
      ┌────▼─────────────▼────┐
      │ errors                │
      │ Problem·ErrorCategory │  ← 最底层：编译层与网关层共用的词汇表
      │ ComfyError·Translator │
      └───────────────────────┘
```

依赖方向单一：`errors` ← `nodeschema` ← `gateway` ← `core` ← `app`。没有反向依赖，
`errors` 不 import 上层，因此不会出现循环。

## 二、`comfybatch_errors.py` — 结构化问题与错误翻译

**为什么放最底层**：编译层（预检发现的问题）与网关层（ComfyUI 返回的错误）需要表达同一类概念，
并且都要变成同一种可展示对象。把它们统一成 `Problem` 之后，UI 只需渲染一种东西，
测试只需断言一种东西，批次止损只需读 `problem.workflow_level`。

### 关键设计

- **`Problem`** — 一个可解释的缺陷：分类、中文标题、节点号与类型、出错参数、当前值、
  合法候选、允许范围、批次影响、可执行修复步骤、原始报文。`render()` 输出单行中文摘要。
- **`Problem.workflow_level`** — 是否应该停批。**它同时要求 `severity == blocking`**：
  一个警告即使分类属于“工作流级”，也不能中止运行。这正是“纯显示节点多出前端状态”
  不会误停批次的原因。
- **`ComfyError`** — 保留 `status`、`raw`、`body`、`path` 的异常。原来的代码丢失了 `raw`。
- **`ErrorTranslator`** — 以 ComfyUI **自带的类型串**为主键（`missing_node_type`、
  `value_not_in_list`、`required_input_missing`、`return_type_mismatch`、`prompt_no_outputs`），
  而不是猜消息文本；文本正则只作兜底。
- **候选值补全** — ComfyUI 在候选很多时把 `input_config` 置空，只在 `details` 里写
  `not in (list of length 44)`。因此 `translate()` 接受一个 `candidate_resolver`，
  从实时 `object_info` 补全候选。**修复步骤在候选补全之后才生成**，否则会漏掉最关键的
  “改用本机已有候选：…”这一步。

## 三、`comfybatch_nodeschema.py` — 模式驱动的编译层

### 3.1 `NodeSchemaRegistry`

对 `/object_info` 的只读封装，提供 `widget_order`、`input_spec`、`combo_candidates`、
`required_input_names`、`coerce`、`validate`。

三个刻意的性质：

- **可以为空**。所有访问器在空注册表下都能工作，编译退化为“不校验但可用”，
  而不是报错。这让软件在 ComfyUI 离线时仍能编译并给出诊断。
- **不做假设**。`_is_widget()` 只把 `INT/FLOAT/STRING/BOOLEAN/COMBO` 以及候选列表
  视为控件，且排除 `forceInput`；其余一律视为连线。
- **可全局安装**。`set_active_registry()` 让 `BatchRunner` 与 `Application` 不必
  把注册表穿过每一层调用。

### 3.2 `WidgetBinder` — 本轮的修复核心

绑定算法（`bind`）：

1. 优先取**节点自己声明**的控件顺序：`inputs[].widget.name`。它对该文件是权威的，
   而且包含了“已转连线”的控件——这正是位置游标漏掉的信息。
2. 声明为空时退回 schema 的 `widget_order`。
3. 与 `widgets_values` 逐槽对齐。**唯一的位置规则**：seed 类控件后面插入一个隐藏的
   `control_after_generate`，其取值必须是 `fixed/increment/decrement/randomize` 之一。
4. 对齐后校验长度。不一致时**再试一次 schema 顺序**；仍不一致则产出问题，列出两侧清单。
5. **按名字覆盖连线输入**，连线优先。

严重程度分级（重要）：

| 情况 | 判定 | 理由 |
|---|---|---|
| 声明 N 个控件，值多于 N 个 | 警告 | 多出的通常是前端显示状态；已绑定的前缀对齐可信 |
| 声明的参数拿不到值 | 警告（仍报告） | 绑定层无法知道转换器或 ComfyUI 是否会补上 |
| 类不在 schema 中 | 警告 | 提交图审计会以“缺少节点”阻断，不该重复阻断 |

**绑定层只诊断，阻断由提交图审计负责。** 这是刻意的职责划分：只有审计看到了最终提交图，
才知道某个值是否真的缺失。

### 3.3 `CONVERTERS` — 声明式转换器注册表

原来的 `elif node_type == ...` 链（约 60 行、20 个分支）换成一张字典，每个条目是
一个 `(ctx, inputs, sources) -> None` 的函数加一个 `seed_policy`。新增节点类型是加一行，
而不是在链尾再挂一个分支。

覆盖 `UltimateSDUpscale` 全部 18 个参数、`KSampler`/`KSamplerAdvanced`、
各类 loader、`ResolutionSelector`、`easy stylesSelector`、`LatentUpscaleBy` 等。

### 3.4 `CompiledGraphAudit` — 第四层预检

对**最终提交图**逐节点逐输入产出：

- `value` 与 `source ∈ {linked, widget, override, injected, default}`（溯源）；
- 类型/候选/范围校验；
- 悬空连线检测；
- `required` 段的必填输入缺失检测。

它同时是两件事的载体：

1. 页面上的“实际生效检查”与参数来源表；
2. 计划书里“页面值与最终提交图一致”的**可断言事实**——`diff_against_page()` 就是
   这一点的一致性检查函数，测试与 UI 共用同一份数据。

## 四、`comfybatch_gateway.py` — 唯一 I/O 接缝

`ComfyGateway` 是一个 `Protocol`，生产实现 `ProductionGateway` 走真实 HTTP，
`FakeComfyGateway` 在内存里返回节点定义、资源清单、成功历史与各类错误。

两个行为是刻意设计的：

- **保留正文**。非 2xx 时读取 `HTTPError.read()`，解析后作为 `ComfyError` 抛出。
- **`poll()` 返回三态**（`pending | done | error`）。`status_str == "error"` 立即判定失败，
  并用 `ErrorTranslator.from_history()` 解释。这正是把失败判定从 1800 秒降到秒级的地方。

`ComfyClient` 保留为兼容门面（`json`/`output` 仍在），因为既有测试与 `Application`
依赖它们；`BatchRunner._poll()` 同时接受新契约（`poll`）和旧契约（`output`），
所以老测试假件无需改动。

## 五、批次止损

`BatchRunner._run` 的失败处理分三层：

| 层级 | 触发 | 行为 |
|---|---|---|
| 工作流级 | `Problem.workflow_level` 为真（缺节点/缺资源/参数越界/悬空/输入缺失） | **首条即停**，剩余任务不再提交 |
| 熔断 | 连续 `max_consecutive_failures` 条任务级失败 | 停止批次 |
| 任务级 | 其余 | 记录后继续 |

另外：报告新增 `audit`、`aborted_reason`、`completed_count` 字段，
状态新增 `aborted`，`/api/status` 把它透出到页面顶部横幅。

## 六、成图预览与打回重做

### `ResultReviewStore`

按运行保存一份 JSON（原子写入：临时文件 + `replace`），存放于
数据目录的 `reviews/<run_id>.json`，**不放在输出目录**——这样清空或移动输出目录
不会丢失审核历史。

- `ingest()` 把一次运行的结果并入文档，**保留已有决定**；当尝试次数增加时，
  旧版本进入 `history` 且状态自动变为 `已替换`，当前有效版本始终是最后一条。
- `confirm()` 支持单张与批量，状态限定为 `待确认/已通过/需重做/已替换`。
- `latest_run_id()` 支持**重启恢复**：运行态只在内存里，但决定在磁盘上，
  所以重开程序后结果页不会空白（标记 `restored`）。

### `BatchRunner.redo()`

四种模式，区别在于“什么被刻意保持不变”：

| 模式 | 保持不变 | 实现 |
|---|---|---|
| `same_seed` | 种子与全部参数 | 直接重发上次的编译图，只改文件名前缀 |
| `new_seed` | 工作流与配置 | 重新编译，种子重新随机 |
| `edited_prompt` | 其它一切 | 替换该条的提示词后重新编译 |
| `reupscale_only` | 原图 | 复用为输入图片；工作流不支持输入图片时给出明确说明而非静默失败 |

重做会追加一次尝试，因此审核文档自动记录版本关系。

## 六-补、软件内资源替换

计划书 P5 要求“资源替换规则、持久化，且禁止静默替换”。实现要点：

### `ResourceOverrideStore`

规则以 **`workflow_fingerprint + node_id + input_name`** 为键持久化到
`resource_rules/resource_rules.json`。指纹进键是刻意的：工作流文件一旦改动，节点编号的含义
可能已经变了，旧规则不得继续悄悄生效。

### 三条防线，确保“不静默”

1. 规则只能由用户在界面里点选候选后创建，没有任何自动匹配逻辑；
2. 编译时覆盖被标记为新的来源 `user_replaced`（中文“用户在软件内替换”），
   与 `override`（软件按配置重算）区分开；
3. 审计同时输出 `replacements` 列表，抽屉的“生效参数”表因此会把用户替换显示出来，
   用户永远能回答“这个值是工作流要的还是我改的”。

### 作用域

| 作用域 | 存放 | 生命周期 |
|---|---|---|
| 仅本次批次 | 页面内存 → `config.resource_overrides` | 关闭页面即失效 |
| 永久规则 | 服务端 `resource_rules.json` | 重启后仍生效，可在抽屉里删除 |

两者合并时以“本次批次的显式选择”优先，且都不覆盖用户在别处显式指定的值。

### 抽屉提供的动作

- 每个“缺资源”问题旁边一个候选项下拉框（候选来自新增的
  `/api/models/upscale_models` 等清单），两个按钮：「仅本次批次生效」「保存为永久规则」；
- 「打开模型目录」按钮（`/api/open-folder`），按 7 个模型目录分别列出，
  引导用户把缺失文件放进去后点「重新检查」；
- 已保存规则的表格，可逐条删除（`/api/resource/forget`），
  这样替换不是单向门。

## 六-补二、种子：可见与可控

`graph_seeds()` 从**编译后的提交图**里取出所有具体整数种子（`seed` 与 `noise_seed`），
写入 `result.generation.seeds`，因此页面上每张图都能看到自己真实的种子——
而不是界面上显示的某个“意图值”。

`apply_seed()` 把图里所有具体种子钉到给定值，并按节点偏移 1，避免多采样器工作流被喂同一个
种子而产生相关性。仍然指向别的节点的连线不做改动（种子的归属在那个节点上）。

两种入口：

| 入口 | 用途 |
|---|---|
| `BatchConfig.seed` | 整批固定种子，适合复现某一版整批结果 |
| `redo(..., seed=N)` | 单张重做时钉住种子，适合“只变种子、其它全不变” |

四种重做方式与种子的关系：

| 模式 | 种子 | 做法 |
|---|---|---|
| `same_seed` | **保持不变** | 直接重发上一次的提交图（`deepcopy`），种子已是具体整数 |
| `new_seed` | 重新随机 | 重新编译，`_randomize_seed` 重新取值 |
| `edited_prompt` | 重新随机 | 重新编译 |
| `reupscale_only` | 重新随机 | 重新编译，以上次输出作为输入图片 |

## 六-补三、参数工作台

`comfybatch_params.py` 里一张声明表同时驱动四件事：页面控件、值域与候选校验、
写进提交图的位置、审计里的来源解释。加一个参数是加一条声明，不是改四个地方——
这是为了防止「页面显示了某个值，但它从没到过 ComfyUI」这类最难查的漂移。

一采/二采的区分不看节点编号（编号没有执行顺序含义），而是沿潜空间链路推导：
某采样器的 `latent_image` 上游若能走到另一个采样器，它就是后一采。

合并优先级：任务级 > 批次级 > 工作流默认值 > 工作流自身值。

参数层有三条「不静默」保证：越界整批不写入、拼错参数名要报出来、
目标输入被连线驱动时明确说明该改哪个参数，并且**永不覆盖指向其他节点的连线**。

## 七、前端

单页，五个阶段保持不变，新增：

- **审图看板**：每张图独立卡片，显示任务号与标题、状态与耗时、实际工作流与**实际分支**、
  模型/风格/LoRA、原始与最终尺寸、正负面提示词、自动检查结论、输出路径、历史版本数；
- **打回重做**：通过 / 打回重做 / 记录问题三个动作，重做方式可选；
- **键盘审图**：`J`/`K` 上下、`Y` 通过、`N` 打回、`Enter` 看原图。45 张以上纯鼠标审核太慢，
  这是计划书之外补的；
- **错误抽屉**：渲染 `Problem` 的中文标题、节点与参数、当前值、合法候选、修复步骤，
  以及可折叠的原始 ComfyUI 报文。任务级错误因此**变得可点击**（V2.13 完全不渲染
  `results[].error`）；
- **来源面板**：把审计的 `overrides` 表格化，逐行显示“节点 / 参数 / 值 / 来源”。

前端只消费服务器状态，不拼接输出目录、不读汇报文件。

## 八、兼容与迁移

- `comfybatch_v2_core.py` 保留为对外门面，既有 50 项测试的 import 与断言不变
  （除 3 项因 HTML 路径假设失败、1 项钉住了非法比例标签，已按事实修正）。
- `ComfyClient` 与 `BatchRunner` 同时支持新旧两种客户端契约。
- 新增 `--data-dir`，开发与联调写独立目录，**不触碰 `%LOCALAPPDATA%\ComfyBatch-S`**
  里现有的 14 条 LoRA 档案与 18 个预设。
- 新增 `--comfy-url` 便于切换 ComfyUI 地址。
