# 负面编码连接点被占用时，软件还能不能继续？

> 讨论对象：`<工作流目录>\▶▷Krea2-极清生图流+SeedVR2-int8图像放大.json`
> 结论先行：**能继续，而且已经跑通了**——但这次实测暴露出三个必须正视的问题，其中一个是**语义级错误**。

---

## 一、先回答你的问题：能继续

我用软件自己的 `Krea2WorkflowAdapter` 直接加载了这个工作流并做了真实的 `build()`，不是推演：

```
--- 不填负面词 ---   ready: True   negative: {"requested": false, "mode": "未填写"}
--- 填写负面词 ---   ready: True   negative: {"requested": true,  "mode": "自动写入或补建 CLIPTextEncode"}
                     errors: []   warnings: []
```

`build()` 也成功了，没有抛错。所以：

**"负面编码的连接点被占用"这个情况，不妨碍软件继续。**

原因在代码里看得很清楚：`_apply_prompt`（`comfybatch_v2_core.py:1569`）**不去抢那个被占用的编码节点**。它的判断顺序是——

1. 先看采样器的 `negative` 输入上挂的是不是 `CLIPTextEncode`；
2. 如果是 → 就地改写那个节点；
3. 如果**不是**（比如挂的是 `ConditioningZeroOut`、`ConditioningCombine` 等）→ **不改它**，转而从正面编码器借一条 `clip` 连线，**新建一个专属的 `CLIPTextEncode`**，再把采样器的 `negative` 改指向这个新节点。

第 1591 行那句 `if graph.get(negative_id, {}).get("class_type") == "CLIPTextEncode"` 就是分水岭：**是编码节点才动它，不是就绕开它另建一个。** 这就是"连接点被占用仍可继续"的机制本身。

## 二、实测结果：这条工作流的真实结构

这是关键。这个工作流的负面链**不是常规写法**，所以我先把它的真实接线摊开。

### 原始文件里（52 个节点，UI 格式）

| 节点 | 类型 | 说明 |
|---|---|---|
| `25` | CLIPTextEncode | 正面（widgets 里是一整段超长正向提示词） |
| `23` | CLIPTextEncode | **标题写着"负面条件"，widgets 里是完整的负面词表** |
| `15` | ConditioningZeroOut | 输入 ← `25`（正面），输出被采样器当负面用 |
| `29` | CLIPLoader | `qwen3vl_4b_fp8_scaled.safetensors` + `krea2` |

**这条流的作者用了一种"负面归零"的技巧**：把 `ConditioningZeroOut(正面)` 的结果当作负面条件喂给采样器（等于"不要任何东西"），而不是用一个真正的负面提示词编码。而那个真正装满了负面词的节点 `23`……

**在原文件里就已经是孤立的**：

```
node 23 ->  (no consumer -> ORPHAN)
node 15 ->  [21] KSamplerAdvanced.negative   (mode=0)
            [13] KSampler.negative           (mode=0)
            [3]  UltimateSDUpscale.negative  (mode=4)
```

节点 `23` 在原始工作流中**没有任何下游连接**。也就是说：**这个工作流原本就没有在用它的负面词表**——`23` 是作者留在画布上的"素材/草稿"，实际生效的负面是 `15` 的归零。

这一点很重要，它决定了后面两个问题的性质。

### build() 之后的实际情况

```
  13 KSampler          negative: ["30",0]     ← 新建
  21 KSamplerAdvanced  negative: ["31",0]     ← 新建
  25 CLIPTextEncode    正面
  30 CLIPTextEncode    {clip:[29,0], text:"测试负面词A"}   ← 软件新建
  31 CLIPTextEncode    {clip:[29,0], text:"测试负面词A"}   ← 软件新建
  15 ConditioningZeroOut  conditioning: ["25",0]           ← 变成死节点
  graph size: 15    node 23 in graph: False
```

## 三、暴露出三个问题

### 问题 1（严重·语义错误）：把 `ConditioningZeroOut` 归零的负面，换成了正向负面词

这是**最需要你拍板的问题**，因为它不是一个 bug 的"实现细节"，而是**改变了出图语义**。

- **原始意图**：`KSampler.negative ← ConditioningZeroOut(正面)`。归零后的 conditioning 是一个"空条件"，语义上等于**不做负面引导**（CFG 的负分支被中和）。这是很多"极清/洗图"流的常见做法——作者根本不想让负面词起作用，因为负面引导会压细节。
- **软件改后**：`KSampler.negative ← 新建的 CLIPTextEncode("负面词")`。语义变成**真正的负面引导**。

也就是说，**只要你在界面上填了负面词，软件就会悄悄把这个流的"负面归零"改成"负面引导"**，而这两者对最终画面的影响是实质性的（尤其这类低 CFG=1 的流，负面分支的行为更敏感）。注意上面的采样器参数：`cfg: 1.0`。**在 CFG=1 时，负面分支理论上应该完全不起作用**——但 `ConditioningZeroOut` 存在的意义恰恰说明作者在防范某些节点/放大阶段对负面的特殊处理。软件把它替换掉，等于单方面推翻了作者的设计。

**这不属于"能安全改的就改"**，而是属于应该**至少警告、最好询问**的改动。它现在的行为是"静默替换"——`errors: []`、`warnings: []`，界面上只会显示一句很乐观的"自动写入或补建 CLIPTextEncode"，用户完全看不出自己的"负面归零"被改成了"负面引导"。

> 顺便说明：这**不是**我上次描述的那套"缺 CLIP 连线才拒绝"的逻辑在起作用——这个流既不缺 `CLIPTextEncode`，正面编码器也拿得到 `clip` 连线，所以两道防线都没触发，`ready: True` 一路通过。

### 问题 2（中等·重复建节点）：两个采样器各建了一个内容相同的负面编码

`30` 和 `31` 是两个独立的 `CLIPTextEncode`，**文字完全一样**，只是分别接给 `13` 和 `21`。

原因在 `_apply_prompt` 第 1585-1613 行的循环：它**按采样器遍历**，每个采样器发现负面口不可复用时都各自新建一个节点；`updated_encoders` 这个去重集合**只在"就地改写已有编码器"那条分支里生效**（第 1592 行），在"新建节点"这条分支里**没有参与判断**。

功能上无害（两段采样用同样的负面词是正确的），但：
- 图变脏了；
- 如果用户之后想单独调第一段的负面词，界面无从下手（两个节点，且没有语义区分）；
- 节点数增长随采样器数量线性膨胀。

**正确做法**是"每个不同的负面文本复用一个节点"——用负面文本或来源编码器 id 做 key 去重。

### 问题 3（轻微·死节点未清理）：`ConditioningZeroOut` 和 `23` 的去留

- `15 ConditioningZeroOut` 在负面口被改指后，**没有任何消费者**了，但**仍留在图里**（`graph size: 15` 里包含它）。它会跟着 API 请求一起发给 ComfyUI。ComfyUI 侧通常无害（未连接的节点不执行），但会白占一次序列化、也会在报错时干扰定位。
- 节点 `23` 反而**被丢掉了**——但这里要说清楚：**丢掉它是"正确的"**，因为它原本就已孤立，`_convert_ui_graph` 第 1490-1502 行的可达性剪枝（从 `SaveImage` 反向收集可达节点）本来就该把它剪掉。**这条不是缺陷，是既有设计在正常工作。**

我把 `23` 写出来，是为了防止一个误判：**"软件的注入把原负面词丢了"——不成立**，原负面词在 `build()` 之前就没接进图。

## 四、这几个问题的共性

三条问题其实是同一个设计取向的两面：

| 软件的原则 | 在这个流上的表现 |
|---|---|
| 不碰"看不懂"的节点，绕开它 | ✅ 绕开了 `ConditioningZeroOut`，成功继续 |
| 绕开时不告诉用户自己绕掉了什么 | ❌ 静默把"归零"变成"引导"（问题 1） |
| 注入时不做节点复用 | ❌ 每采样器建一个（问题 2） |
| 不清理被绕开的残留 | ❌ `15` 变死节点留下（问题 3） |

**它的"绕开"策略本身是对的、且正是你问的能力所在**（被占用就另起一个，不硬抢）。问题出在**绕开的代价没有被说出来**，以及配套的复用/清理没做。

## 五、建议（未动代码，等你定）

按性价比排序：

**A. 先加"语义变更警示"（最高优先，改动最小）**
构建前判断：采样器负面口挂的是非 `CLIPTextEncode` 的 conditioning 节点（如 `ConditioningZeroOut` / `ConditioningCombine`）时，**必须**产生一条 warning，写清"该流原使用 X 节点处理负面，填写负面词后将改为直接负面引导"。让用户至少知道发生了什么。这是**止损**级改动，不改变行为。

**B. 再考虑"要不要拦"**
更进一步的选择有三种，需要你定：
1. **仅警告**（推荐）：照旧替换，但明确提示；
2. **可选开关**：界面上给一个"保留工作流原有负面处理（不替换）"，勾了就把负面词写进 `23` 那类孤立编码器、但不动采样器连线（此时负面词不生效，纯留档）；
3. **直接拒绝**：像缺 CLIP 连线那样报错，逼用户手动改工作流。**我不建议**——这个流本身是能安全处理的正经流，拒绝会误伤。

**C. 负面节点复用去重**（低风险，纯优化）
在 `_apply_prompt` 的新建分支里加入按负面文本 key 的复用表，让 `30`/`31` 合成一个。

**D. 死节点清理**（低风险，可选）
注入完成后，扫一遍"无任何消费者且非 `SaveImage` 输出"的 conditioning 类节点。**建议只做标记不做删除**——万一作者的画布里有靠 `rgthree` 的分组旁路器（这个流里就有 3 个 `Fast Groups Bypasser (rgthree)`）控制的分支，贸然删可能误伤。

---

## 六、一句话总结

> **能继续。** 软件用的是"绕开被占用的连接点、另建专属编码节点"的策略，实测 `ready: True`、`build()` 成功。
> **但它同时静默地推翻了这个流"负面归零"的设计**——因为原作者用的是 `ConditioningZeroOut` 而不是真正的负面编码器。这是我这次实测最想让你知道的一件事，也是唯一一个我认为**必须修**的点。
> 另外它给每个采样器各建了一个重复节点，`ConditioningZeroOut` 变成死节点残留。
