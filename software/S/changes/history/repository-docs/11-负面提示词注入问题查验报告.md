## 问题 1：负面锚点被静默替换 ✅ 复现

### 证据

`run/_verify_negative.py` 对真实工作流执行 `build()`：

```
capabilities.ready    : True
capabilities.errors   : []
capabilities.warnings : []          ← 关键：没有任何警告
negative_prompt 报告  : {"requested": true, "mode": "自动写入或补建 CLIPTextEncode"}

build() 后采样器负面口指向：
  [13] KSampler           negative -> [30] CLIPTextEncode     ← 原为 [15] ConditioningZeroOut
  [21] KSamplerAdvanced   negative -> [31] CLIPTextEncode     ← 原为 [15] ConditioningZeroOut
```

### 机制

`_apply_prompt`（`comfybatch_v2_core.py:1591`）：

```python
if graph.get(negative_id, {}).get("class_type") == "CLIPTextEncode":
    ...  # 就地改写
    continue
# 否则：从正面编码器借 clip，新建节点，改指采样器
sampler_inputs["negative"] = [injected_id, 0]
```

原始语义 `ConditioningZeroOut(正面)` = 空条件（不做负面引导）；替换后 = 真负面引导。
两条防线都没触发，因为该流既不缺 `CLIPTextEncode`（有 23、25），正面也拿得到 `clip` 连线。

### 为什么是缺陷

这不是"实现细节"，是**出图语义被改变**，而界面上只有一句乐观的"自动写入或补建 CLIPTextEncode"，用户无从察觉。注意该流 `cfg = 1.0`。

## 问题 3：死节点残留 ✅ 复现

### 证据

```
'15' 是否仍在图中 : True
谁消费 15          : (无人 -> 死节点)
'23' 是否仍在图中 : False
23 在原始文件中被谁消费: (无人 -> 原文件即孤立，剪枝正确)
```

### 判定

- `15 ConditioningZeroOut` 在负面口被改指后失去全部消费者，**仍留在图里**（`graph size: 15` 含它），会跟着 API 请求发给 ComfyUI。
- 节点 `23` 的消失是 `_convert_ui_graph` 第 1490-1502 行可达性剪枝的**正常行为**，**不是**注入造成的。此项列出仅为防止误判。

## 问题 4（新发现·严重）：作者原有负面词被静默丢弃 ✅ 复现

### 证据

用最小图（采样器负面口**直连** `CLIPTextEncode`，作者写了 `"作者原有的负面词"`），对比两种注册表：

| 环境 | `node4.text` 结果 | 原词保留 |
|---|---|---|
| **空注册表**（未连 ComfyUI / 定义未加载） | `"新增负面词B"` | ❌ **丢失** |
| **真实注册表**（`tests/fixtures/object_info.json`） | `"新增负面词B, 作者原有的负面词"` | ✅ 保留 |

`run/_verify_real_registry.py` 实测输出：

```
CLIPTextEncode 控件顺序 : ['text']
  [空注册表]   node4.text = "新增负面词B"                    保留原词? False
  [真实注册表] node4.text = "新增负面词B, 作者原有的负面词"   保留原词? True
```

### 机制（两层）

**第一层·注入侧**：`_apply_prompt` 第 1593-1596 行**本意**是"叠加作者原词"：

```python
current = str(graph[negative_id].setdefault("inputs", {}).get("text", "")).strip()
graph[negative_id]["inputs"]["text"] = PromptCompiler.compile_negative(
    negative_text, BatchConfig("", "", negative_prompt=current)
)
```

`compile_negative` 的叠加语义**已验证正确**：

```
compile_negative('新增负面词B', negative_prompt='')          -> '新增负面词B'
compile_negative('新增负面词B', negative_prompt='作者原有的负面词') -> '新增负面词B, 作者原有的负面词'
```

所以"叠加"本身没问题——**问题是 `current` 读到的就是空串**。

**第二层·绑定侧（根因）**：`CLIPTextEncode` **不在 `CONVERTERS` 注册表里**（`comfybatch_nodeschema.py:728-751`，实测 `'CLIPTextEncode' in CONVERTERS == False`）。它走通用 widget 绑定，而控件顺序靠 schema 推断。注册表为空时：

```
declared widgets : []
strategy         : none
widgets 映射结果 : {}
problems         : ['无法确定控件顺序']
```

因此 UI 图里 `widgets_values: ["作者原有的负面词"]` **从未被写进 `inputs.text`**，`inputs` 里只剩连线 `{"clip": [...]}`。**触发条件已实测确认**：真实注册表下正常，空注册表下丢失。

---

## 横向影响：为什么问题4 值得优先

问题4 的影响面**比问题1更广**，因为它打中的是**最常见的正常写法**：

- 问题1 只在"负面口挂 `ConditioningZeroOut` 等非编码器"时触发（较特殊）；
- 问题4 在**任何**"负面口直连 `CLIPTextEncode` + 作者写了负面词"的工作流上触发，**只要注册表为空**。

而"注册表为空"并不是罕见状态——它出现在节点定义尚未加载时（软件刚启动、ComfyUI 未就绪、自定义节点缺失）。

**后果**：把负数条件的原始约束替换成空白基线。UI 图下采样的 `positive` 输入走的是 `_conditioning_encoder` + `PrimitiveStringMultiline` 路径（`_apply_prompt` 第 1570-1576 行），**不依赖 widget 绑定**，所以正面词正常；只有负面这条依赖 `inputs.text` 的路会丢。**不对称**，因此更隐蔽。

## 修复建议（按优先级，均未动代码）

### P0 — 问题4：让 `CLIPTextEncode` 有确定的控件映射

两条路，建议**同时做**：

1. **加转换器**：在 `CONVERTERS` 注册 `"CLIPTextEncode": Converter(...)`，从 `widgets_values` 明确取 `text`。与 `_primitive_string` 同构，改动小、确定性最高。
2. **补 schema 兜底**：为常见核心节点（`CLIPTextEncode` / `KSampler` / `EmptyLatentImage` 等）内置一份"无注册表时的控件顺序"表，避免空注册表下退化成 `strategy="none"`。

**验收**：新增测试——UI 图 + `widgets_values=["作者原有的负面词"]` + **空注册表**，断言 `build()` 后仍含该词。

### P1 — 问题1：语义变更必须提示

在 `capabilities()` 里判断：负面口挂的是非 `CLIPTextEncode` 的 conditioning 节点时，产生 warning（不改行为，纯止损）。文案需说明"原工作流使用 X 节点处理负面，填写负面词后将改为直接负面引导"。

**验收**：新增测试断言 `warnings` 非空且含节点类型名；**并修改第 431 行那个把缺陷当规格的测试**。

### P2 — 问题2：负面节点按文本复用

`_apply_prompt` 新建分支引入按负面文本 key 的复用表，让 `30`/`31` 合一。

**验收**：两采样器场景断言只新增 1 个编码节点。

### P3 — 问题3：死节点只标记不删

建议**不删**：该流含 3 个 rgthree `Fast Groups Bypasser (rgthree)`，删除有误伤旁路分支的风险。可在审计报告里列出孤立的 conditioning 节点供用户判断。
