## 零、先说一处必须更正的结论（重要）

**上一份报告（`docs/11`）里的「问题 4」被夸大了，现予降级。**

原报告称：`CLIPTextEncode` 不在 `CONVERTERS` 里 → 空注册表下 `widgets_values` 无法绑到 `inputs.text` → 作者原有负面词被静默丢弃，且认为触发面很广。

**实测更正**：真实 ComfyUI 导出的 UI 图里，节点**自带 `widget` 声明**：

```json
{ "name": "text", "widget": {"name": "text"}, "link": null }
```

`WidgetBinder.declared_widgets()`（`comfybatch_nodeschema.py:342`）正是读 `inputs[].widget`，所以 `declared=['text']`、`strategy='declared'`，**与注册表是否为空无关**。对照实测（`run/_verify_corrected.py`）：

| 图的形状 | 空注册表 | 真实注册表 |
|---|---|---|
| **带 `widget` 声明（真实导出）** | `strategy=declared` ✅ 原词保留 | ✅ 原词保留 |
| 无 `widget` 声明（我上轮的合成图） | `strategy=none` ❌ 原词丢失 | `strategy=declared` ✅ 保留 |

**结论**：问题 4 只在"图缺少 `widget` 声明"这一**非常规形状**下出现，**对真实工作流不成立**。我上一轮用了一个省略 `widget` 键的合成图，得出了过度泛化的结论——这是我的方法错误，已修正。

**但保留下述真实的次级发现（问题 5，见第三节）**：当有节点类型既无 `widget` 声明、注册表也查不到时，`WidgetBinder` 只产生一条 `severity=WARNING` 的"无法确定控件顺序"，**不阻断**。若该节点恰好是**负面编码**，负面词会被静默丢弃。这是**真实的窄口风险**，值得加固，但不是普遍问题。

## 一、确认成立的问题

### 问题 1：非编码器负面锚点被静默替换（`ConditioningZeroOut` → 真负面编码）

**证据**（`run/_verify_negative.py`）：

```
capabilities.ready=True   errors=[]   warnings=[]      ← 零提示
negative_prompt 报告: {"requested": true, "mode": "自动写入或补建 CLIPTextEncode"}
build() 后:
  [13] KSampler          negative -> [30] CLIPTextEncode   (原 [15] ConditioningZeroOut)
  [21] KSamplerAdvanced  negative -> [31] CLIPTextEncode   (原 [15] ConditioningZeroOut)
```

**机制**：`_apply_prompt`（`core.py:1591`）——负面口挂的不是 `CLIPTextEncode` 时，不抢它，改从正面编码器借 `clip` 连线新建节点并改指。

**严重度修正：中（原判"严重"过高）**
该流 `cfg=1.0`，CFG 公式退化为 `out = pos`，负项被消掉，**当前设置下语义虽变、结果不变**。真正的风险是：**用户一旦调高 `cfg`**，负面分支立即生效，而用户不知道接的是自己填的词还是被替换掉的节点。对 `cfg>1` 的一般工作流，这是实打实的语义变更。

**修复方向**：不改变注入行为，**补一条 warning**，说明"该工作流原使用 X 节点处理负面，填写负面词后将改为直接负面引导"。

---

### 问题 2：负面编码节点重复创建

**证据**：新建 `[30]`、`[31]` 文本完全相同（`"测试负面词A"`），节点数 2、文本去重后 1。

**机制**：`_apply_prompt` 第 1585-1613 行按采样器循环；`updated_encoders` 去重集合**只在"就地改写"分支写入**（1592/1597），**"新建"分支不参与判断**。

**严重度**：低（功能正确，仅图脏；但用户无法单独调某一段的负面词）。

**修复方向**：新建分支引入按负面文本 key 的复用表。

---

### 问题 3：被绕开的 conditioning 节点残留为死节点

**证据**：`'15' 仍在图中 = True`，但**无任何消费者**（`_verify_negative.py`）。

**机制**：`_apply_prompt` 改指采样器 `negative` 后不清理 `15`；`graph` 也不含"无消费者即剔除"的步骤（可达性剪枝 `core.py:1490-1502` 只在上游方向上做，且发生在 `_apply_prompt` **之前**）。

**严重度**：低（ComfyUI 不执行未连接节点，但干扰报错定位、白占序列化）。

**修复方向**：**只标记不删**——该流含 3 个 rgthree `Fast Groups Bypasser (rgthree)` 控制的分支，删除有误伤风险。列入审计报告即可。

---

### 问题 5（新·窄口风险）：无 widget 声明 + 无注册表时，负面词被静默丢弃

**证据**（`run/_verify_corrected.py`，第一行）：

```
--- 无 widget 声明 + 空注册表 ---
    bind strategy=none   declared=[]
    node4.text = "用户填的负面词"      作者原词保留? False
```

**机制**：`WidgetBinder.bind()`（`nodeschema.py:389-411`）在 `declared` 为空且注册表无该类型时，只追加一条 `severity=WARNING` 的 `Problem` 然后 `return`——**不阻断**。因此该节点的 `text` 永远为空，`_apply_prompt:1593` 读到的 `current` 是空串。

**为何仍值得修**：真实工作流不走这条路（见更正），但**手写/第三方转换的图**可能省略 `widget` 键；此时若该节点是负面编码，**用户看到"注入成功"、实际丢了负面词**。属"静默降级"，与本项目既定的"不能安全改就报错"原则不一致。

**修复方向**：为少量核心节点内置"无注册表时的控件顺序"兜底表（`CLIPTextEncode: ['text']`、`KSampler`、`EmptyLatentImage` 等）；或者当**被丢弃的节点是负面编码且用户填了负面词**时，升级为阻断。

## 三、对用户那句问题的最终答复（已确认）

> **"我接入的负面词会不会因为这些问题而不影响出图？"**

**分三种情况，实测结论：**

| 工作流形态 | 你的负面词是否影响出图 |
|---|---|
| **该极清流**（负面口挂 `ConditioningZeroOut`，`cfg=1.0`） | **已如实写入提交图**（`[30]`/`[31]` 文本 = 你的词）；但 `cfg=1.0` 使负面分支**在数学上不起作用**——这是该流的设置决定的，**不是软件的问题**。若调高 `cfg`，立即生效 |
| **一般工作流**（负面口直连编码器，`cfg>1`） | **正常生效**，且**作者原负面词一并保留**（`"你的词, 作者原词"`） |
| **完全无 `CLIPTextEncode`** | 软件**拒绝启动**并报错（`test_comfybatch_v2_core.py:448` 已覆盖），不会静默跑 |

**一句话**：你的负面词**每次都进了提交图**；当前看不到效果，是 `cfg=1.0` 的数学结果，而非注入缺陷。问题 1 的真实危害是"改 `cfg` 后来源不明"，问题 2/3 是图脏，问题 5 是窄口静默降级。
