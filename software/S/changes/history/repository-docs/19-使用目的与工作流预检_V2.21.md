# 使用目的与工作流预检（V2.21）

这份文档回答一个问题：**用户拿一个工作流去干某件事之前，软件怎么知道它干得了。**

---

## 一、要修的是一次"成功"的失败

原来的失败长这样：用户想要放大，于是挑了一个没有放大分支的工作流。批次跑完、报"完成"、
每张图都正常落盘——**只是每一张都不是他要的**。页面上没有任何一处说过这个工作流干不了
这件事，因为在那之前，软件根本没有"用户想干什么"这个概念。

所以这一项做的不是加一个下拉框，而是**把用途声明变成可校验的条件**：选了用途，预检就
必须回答"工作流满足吗"；不满足就阻断，并说清缺哪一环。这与项目的第一原则一致——
不静默。

---

## 二、六种使用目的

用途按**生成管线**划分，而不是按题材划分。原因很直接：管线的每一段都能从提交给
ComfyUI 的图里验证，而题材只是提示词里的字。

| 用途 | id | 判定依据 |
|---|---|---|
| 文生图 | `txt2img` | 采样器的潜空间来自空潜空间节点，不需要输入图 |
| 图生图／参考图 | `img2img` | 有一张输入图经编码后进入采样器 |
| 局部重绘 | `inpaint` | 有内补／遮罩节点进入采样器 |
| 高清重绘（二采） | `refine` | 有一个采样器的潜空间来自另一个采样器 |
| 放大超分 | `upscale` | 有一条放大链路在采样之后、保存之前 |
| 批量变体 | `variants` | 图里有可以直接写入的具体种子 |

这六种与项目自己的语言是对齐的：`01-S完整研发计划` 的专项验收里就写着"正确识别二采、
高清重绘和 SeedVR 放大三个分支"，而这里把"二采"和"放大"拆成了两种用途——因为它们
在工作流里确实是两段不同的链路。

---

## 三、第五层预检

原有四层预检（结构、资源、参数、编译结果）都回答"这个工作流能不能跑"。第五层回答的是
另一类问题："**就算能跑，它是不是在干你要它干的事**"。

判定放在 **编译后的提交图** 上，而不是工作流文件上。理由和第 8 项读回实际种子是同一条：
工作流文件说的是意图，提交图才是事实——分支是启用的还是静音的、连线被重新指向哪里，
只有编译完才确定。位置在 `CompiledGraphAudit.run()`，结论进同一份 `problems` 列表，
所以它天然走 preflight 已有的阻断通道、错误抽屉和「重新检查」入口，不需要新的一套 UI。

判定结果同时挂在 `audit.purpose` 上，供页面显示：

```json
{
  "id": "upscale", "name": "放大超分", "summary": "把结果放大到更高分辨率再保存",
  "checked": true, "unknown": false, "ready": false,
  "requirements": [
    {"key": "sampler_to_save", "label": "至少一个采样器的结果能通到保存节点",
     "met": true, "evidence": "节点 13（KSampler） → 节点 21（SaveImage）", "hint": ""},
    {"key": "upscale_branch", "label": "有一条放大链路在采样之后、保存之前",
     "met": false, "evidence": "", "hint": "保存的图片没有经过放大环节；……"}
  ],
  "detail": "使用目的「放大超分」要求：……当前工作流不满足：……",
  "supported": ["txt2img", "refine", "variants"]
}
```

`supported` 是"这个工作流实际支持哪些用途"，用来让阻断信息以可选项结尾，而不是只
说哪里不对。

## 四、判定口径（以及刻意避开的坑）

规则全部基于**结构**，并尽量少依赖类名枚举——类名有 2848 个，枚举不完，也容易漏。

| 判定 | 口径 | 为什么这么做 |
|---|---|---|
| 是不是采样器 | 节点**自己声明了 `latent_image` 输入** | 比列举 `KSampler` 家族稳：本机有几十个采样器包装节点，而且这样永远不会把放大器和采样器搞混（实测：没有任何放大器声明 `latent_image`） |
| 空潜空间 | 类名以 `Empty` 开头 | 覆盖 `EmptyLatentImage`、`EmptySD3LatentImage`、`EmptyChromaRadianceLatentImage`、`Empty Latent (Image Saver)` 等 |
| 输入图 | 类名含 `LoadImage`／`LoadImages`／`LoadImagePath` | `LoadImage`、`LoadImageOutput`、`LoadImageFromUrl`、`VHS_LoadImagePath` 都在内 |
| 放大超分 | 类名含 `upscale` 或 `seedvr`，且**排除 `loader` 与 `latent`** | 只看 `scale` 会把 `ImageScale`、`ImageScaleBy`、`RescaleCFG`、`NumberScaler` 这类只管改尺寸的也算成放大器——本机实测 57 个类名会命中，收紧后 33 个，剩下的都是真的超分节点。放错的代价是"闸门放行、拿回一张只是改了尺寸的图"。`UpscaleModelLoader` 含 `upscale` 但只是选文件；`LatentUpscaleBy` 是潜空间放大，属于"高清重绘"那一半 |
| 局部重绘 | 类名含 `inpaint`，或 `SetLatentNoiseMask` | 同样以本机真实节点名对照过 |
| 二采 | 某个采样器的潜空间闭包里还有另一个采样器 | 与节点编号、类型都无关，只看链路——这正是 `docs/05` 里区分一采二采的同一套办法 |

一个必须注意的细节：**输入图必须真的进入采样器**才算数。图里放着一个没接线的
`LoadImage`，或者一个接在别处的遮罩，都不是"能图生图""能局部重绘"。测试里专门钉了
这两种假阳性。

## 五、不指定用途，就什么都不拦

- **不指定**（空字符串）是一种合法状态：不做任何断言，也不阻断任何东西。V2.20 的行为
  完全不变，这道闸门是用户主动打开的。
- **未知用途**（比如拼错成 `upscale2`）会被**阻断**，而不是被悄悄当成"没指定"。
  后者会把一个拼写错误变成"页面上看起来一切正常"，正是这一项要消灭的那类静默。
  因此 `BatchConfig.from_dict` 原样保留未知的用途字符串，不在配置层就把它抹掉。

阻断时给的三条出路：补齐缺失阶段后重新检查、改选这个工作流真正支持的用途、或者改回
不指定。

## 六、页面

- 主配置区新增「使用目的」下拉框（在「执行分支」右边，因为它就是对分支的约束）。
- 真相栏新增「用途」一行，任何阶段可见：`放大超分 · 工作流不支持（缺：有一条放大链路
  在采样之后、保存之前）`；还没检查过就写「未检查」，不会把没核对说成通过。
- 选择框下方给一条结论式提示；判定不通过时用强调色标出，并把"这个工作流支持什么"
  一起列出来。
- **六项选项由服务端提供**：随 `/api/configure` / `/api/inventory` 回来的
  `inventory.purposes` 就是判定所依据的那份规则，页面照它渲染。页内那份列表只是
  兜底，否则口径一改，页面会提供一个服务端已不认识的用途，然后每一批都被判成
  "未知用途"——一个只有改规则时才会发作的静默故障。
- **切了分支而没重新检查时，旧判定不许冒充当前选择**。判定是对某一次编译做的：
  换了分支但没重新检查，真相栏和提示条都显示「待重新检查」。服务端在编译失败时会
  用**上一次**的检查结果作答（既有行为），此时 `effective` 里的判定可能是别的分支的，
  这个守卫就是为它准备的。要核对判定，看 `preflight.audit.purpose`，那是本次编译的。

## 七、边界（这一轮刻意不做的）

- **用途不进入预设**：预设目前只存风格与 LoRA（`savePreset` 只提交这两样），用途是
  一次批次的目的，不是可复用的样式资源。要加需要先扩预设的数据结构，属于独立需求。
- **用途结论不写进批次报告**：报告里有 `seed_stats` 这类统计，但用途是"批次开始前的
  一道闸门"，通过之后就没有第二次判定，写进每一张图的结果里属于重复。判定在
  `audit.purpose` 与真相栏里可查。
- **判定依赖类名模式**：遇到本项目从未见过的第三方放大/内补节点，可能判成"不支持"。
  这是刻意选择的失败方向——拦错了用户能看见原因并且可以改回「未指定」，而漏判会让
  用户拿到一批不是他要的图且毫无提示。

## 八、真实工作流验收（本机实测）

用本机真实 ComfyUI 与真实工作流（Krea2-极清生图流 + SeedVR2-int8图像放大，含三个保存
分支 `save:6` / `save:94` / `save:1`）跑五组用例，提示词取自桌面 `01.docx` 第 1 条。
驱动脚本在 `run/_purpose_accept.py`（`run/` 不进仓库）。

### 分支反查：同一份工作流、同一个用途，只有对的分支能过

| 分支 | 名称 | 放大超分判定 |
|---|---|---|
| `save:6` | ①Krea2-二采出图2 | 阻断 · 缺 `upscale_branch` |
| `save:94` | SeedVR2-7/3b-int8图像放大 | **无法编译**（该分支没有可写入提示词的节点） |
| `save:1` | ②Krea2-高清重绘2 | 通过 |

这里有个容易看错的地方：`save:94` 的名字里写着"图像放大"，但它编译不出可提交的图；
真正能放大的反而是 `save:1`（含 `UltimateSDUpscale`）。所以**不能拿
`variants[].upscale_count` 判断能不能放大**——那个数只说明"分支里有放大节点"，
`save:6` 的 `upscale_count` 还是 1，可它保存的图压根没经过放大器。用途判定问的是更窄
也更对的那个问题。

### 五组用例

| 用例 | 用途 | 分支 | 结果 | 输出尺寸 |
|---|---|---|---|---|
| A | 文生图 | `save:6` | 通过并出图 | 1456×816 |
| B | 放大超分 | `save:6` | **HTTP 400 拦下，未出图** | — |
| C | 放大超分 | `save:1` | 通过并出图 | **2912×1632** |
| D | 不指定 | `save:6` | 通过并出图（V2.20 行为不变） | 1456×816 |
| E | `upscale2`（拼错） | `save:6` | **HTTP 400 拦下** | — |

C 的尺寸正好是 A 的两倍，说明那张图确实走过了放大器，而不是"闸门放行了一张没放大的图"。
B 拦下时的原文：

> 使用目的「放大超分」要求：有一条放大链路在采样之后、保存之前。当前工作流不满足：
> 保存的图片没有经过放大环节；请在 ComfyUI 里启用带放大器的保存分支，或改选支持放大
> 的工作流（本项目的放大模型参数也需要这条链路才有意义）。

E 拦下时的原文：

> 「upscale2」不是已定义的使用目的，无法按它校验工作流。可选：txt2img、img2img、
> inpaint、refine、upscale、variants。

`/api/start` 与预检走同一个校验入口，所以把接口当后门也绕不过这道闸门。
