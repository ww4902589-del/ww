# 分段生成、下一段与断点续跑（V2.21）

> 任务编号：S-ComfyBatch 任务清单 #6
> 分支：`handoff/local-s-segment`　基点：`8b8361b`（V2.20 发布提交）
> 相关文件：`src/comfybatch_v2_core.py`、`src/comfybatch_v2_app.py`、`src/app.js`、`src/index.html`、`src/app.css`

## 1. 这个功能解决什么

一整批两三百张，跑起来要几个小时。跑完之后才发现前面几十张的构图就偏了，
或者跑到一半程序被关了、电脑重启了，之前跑的全白跑——这是原本的两个痛点。
原来的「暂停／继续」只解决「同一批次里暂停提交新任务」，一旦进程不在，批次就没了。

本功能把批次切成**段**，并且把**进度落盘**：

- **段**：跑到设定条数就停下，等人确认再继续；
- **下一段**：确认没问题，点一下接着跑下一段；
- **断点续跑**：进程中断／关页面／重开软件之后，从**第一个未完成编号**接着跑，
  已完成的那些不重跑。

## 2. 口径（属产品决策，先写清楚待确认）

任务清单、Issue #2、`docs/00`、`docs/15`、`HANDOFF.md` 的后续清单里都只有
「分段生成、下一段与断点续跑」这一行标题，**没有任何既定口径**；全仓检索
`segment`／`断点`／`续跑`／`下一段` 也没有任何既有实现。所以以下是本任务的落地口径，
若与预期不符，改的是这一节，不是实现：

| 概念 | 取值 | 说明 |
|---|---|---|
| 每段条数（`segment_size`） | `0`（默认）～ `1000` | `0` = **不分段**，整批一口气跑完，等价于原行为。默认必须是 0：改成别的值等于替用户做了「每 N 张就停」的决定。 |
| 任务编号（`task_range`） | 空白、`11-20`、`1,3,8-10` | 空白运行全部；填写后只预检和运行所选任务，保留导入时的原编号。 |
| 段边界 | 每完成 `segment_size` 条 | 队列**停住但不销毁**，状态变成 `segment`，等一个「下一段」。 |
| `segment_size` 的计数 | 按**本次运行**数，不按绝对编号 | 否则续跑时第一条就立刻撞到边界，队列原地打转。 |
| 「下一段」 | `POST /api/segment/next` | 只有停在边界（状态 `segment`）时才有效，否则 400。 |
| 断点续跑 | `POST /api/segment/resume` | 从快照里的第一个未完成编号接着跑；快照保留所选任务和首次整理后的提示词，避免重新调用 LLM。 |
| 「可续跑」的判定 | 所选编号中仍有未完成项 | 批次因失败收尾时仍可补跑；旧快照沿用 `next_index <= total`。 |
| 队列还活着时 | 不报「可续跑」 | 否则等于劝用户往同一个 run 里塞第二个队列。 |

`BatchConfig` 里原本有一个**从未被任何代码读取**的 `trial_first` 字段，注释写着
「跑一条后暂停等确认」。本次把它接管为 `segment_size` 的兼容入口：给出
`trial_first=true` 而没有 `segment_size` 时，等价于每段 1 条。老配置不会突然失灵。

## 3. 实现

### 3.1 进度快照（`RunProgressStore`，`core.py`）

- 一份 run 一个文件：`<数据目录>/runs/<run_id>.json`；
- **原子写**：先写 `.tmp` 再 `Path.replace`；Windows 读者短暂占用目标文件时重试替换；
- **先写快照再发布状态**：这样页面看到的进度不会比磁盘上更新，反过来才是危险的方向；
- `run_id` 到 `snapshot()` 之间会落到文件系统，所以读、写、删除都只接受字母数字与 `-_`，
  其它一律拒绝——一个构造出来的 id 不能用来跳出快照目录；
- `next_index` 由**所选编号中的第一个未完成项**推导，不靠计数器：某一条失败、批次继续往下跑之后，
  这个值仍然是对的；
- 快照字段：`run_id / status / updated_at / segment_size / total / selected_indexes /
  completed_indexes / next_index / prompts_refined / output_dir / bundle / config / results`；
- `config` 原样冻结（含 `llm.api_key` 先清空）：续跑必须是**用户当初确认过的那个批次**，
  而不是把同一批路径重新解析一遍。首次整理后的提示词也冻结入快照，续跑不再请求 LLM。
  密钥与批次报告同规则，**不落盘**。

### 3.2 队列（`BatchRunner`）

- 新增 `segment_size` 状态与 `_next_segment` 事件；
- `pause()` 只在状态是 `running` 时生效。原先它在分段边界也会清掉 `_resume` 却不改状态，
  结果是队列看起来还在等确认、实际上再也不会动（**静默冻住**，已修）；
- 状态新增 `segment`，与 `starting/running/paused` 一起并入 `ACTIVE_STATUSES`；
- `start()` 增加 `resume=`，续跑时沿用原来的 `run_id` 并跳过已完成的行；
- 结果按索引覆盖写（`record()`）：被重跑的那条替换掉它自己那行失败记录，
  不会在结果里留下两条。

### 3.3 页面

- 第三阶段新增「分段生成」一块：「每段条数」输入框 + 「下一段」按钮；
- 「下一段」只在**真的停在边界**时可用；提交请求的那几秒里，650ms 一次的轮询
  不能把它重新点亮（正在提交的按钮带 `busy` 类，状态渲染会跳过它）；
- 新增续跑提示条：`共 N 条，已完成 M 条，还有 K 条没跑（从第 00X 条接着跑）`，
  并把「停在分段边界」与「上次没跑完就关了软件」分开说——后者点「下一段」是没有用的；
- **推送与轮询两条路径都给 `resumable`**：`/api/status` 与 SSE 快照各带一份。
  只在轮询里给，页面在推送路径上就永远看不到续跑按钮（页面主要靠推送渲染）。

## 5. 真实生图验收

真 ComfyUI（`127.0.0.1:8188`）+ 真工作流 `▶▷Krea2-高清生图优化流(整合).json`
分支 `save:305`（①Krea2-初生图），模型 `krea2_turbo_int8_convrot.safetensors`，
提示词取自桌面 `01.docx` 前 4 条，隔离实例 `8793`，数据目录与输出目录都在仓库之外。

**A：分段 + 下一段**
1. 每段 2 条启动 → 跑完 2 张后停在边界：`status=segment`、`next_index=3`、
   `total=4`、`results=2`、`snapshot_error=""`、落盘快照 1 份、队列存活期间 `resumable=null`；
2. 点「下一段」→ `completed=4`、`next_index=null`、`resumable=null`；
3. 输出目录 4 张图：`001-贴锋一瞬` 939KB、`002-悬崖抚弦` 1.2MB、
   `003-空座余响` 578KB、`004-梯上失衡` 1.2MB。

**B：断点续跑（真杀进程）**
1. 清空输出与快照，每段 2 条启动，停在边界（2 张图）；
2. **杀掉 8793 进程**，用同一个数据目录重启（等同用户重开软件）；
3. 重启后 `/api/status` 给出 `resumable = {total:4, completed:2, next_index:3, status:"segment"}`；
4. `POST /api/segment/resume` → 200，且把 4 条提示词合集还给了页面；
5. 跑完 `completed=4`、`errors=0`；落盘 4 张，
   **重启前那 2 张的大小与 `mtime_ns` 逐字节一致（未被重跑）**，另外 2 张是本次新生成。

**C：续跑用的必须是当初那份配置**
快照里 `config.segment_size=2`、`bundle.items` 4 条、`config.llm.api_key` 为 `null`
（密钥不落盘），与设计一致。

### 验收中发现的两件事（都不是本功能引入的，留给后续任务）

1. **`/api/configure` 不落盘。** 它只改内存：进程重启后 `comfy_root` 回到默认的
   `~/ComfyUI`，于是续跑的批次会去错地方找图（本次验收第一轮就撞上了，报
   `在 <用户目录>\ComfyUI\output\... 找不到文件`）。桌面页面每次加载都会 POST
   一次 `/api/configure`，正好盖住了这件事；**脚本或无头用法必须自己补这一步**。
   是否要把这几个目录真正持久化，是一个独立的产品决定，本任务不动。
2. **编辑工具会把整份文件写成 LF。** 本仓行尾是逐文件、甚至逐行混排的：
   `comfybatch_v2_core.py` 全 CRLF 但 `roots = [self.comfy_root / "models" / "loras"]`
   那一行是裸 LF；`test_page_assets.py` 的 workbench 测试那一段（335–409 行，74 行）
   也是裸 LF；`comfybatch_v2_app.py` / `index.html` 全 LF；`app.js` / `app.css` 全 CRLF。
   提交前必须按这个约定逐文件还原，否则 diff 会出现整份文件的噪音
   （本次 `core.py` 一次就是 6842 行）。还原脚本应是「按 HEAD 对齐、未改动行原样搬字节、
   新增行沿用相邻行行尾」，**不要**在拼行尾时既写完整行尾又用 `join("\n")`——
   那会给每个新增行多造一个空行。
