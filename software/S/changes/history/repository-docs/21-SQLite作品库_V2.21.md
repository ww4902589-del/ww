# SQLite 本地作品库（任务清单第 4 项）

> 分支：独立分支 `handoff/local-s-library`（与 #3／#6／#8 并行）
> 基点：`8b8361b`（V2.20 发布提交）

## 1. 口径从哪来（先说清楚）

本分支的 `docs/` 里**没有**第 4 项的口径：`HANDOFF.md` 的后续清单里只有一行标题
「SQLite 本地作品库」，全仓 grep `sqlite` 也只命中那行标题本身，也没有第三方依赖
（`sqlite3` 是标准库，不引入新依赖，PyInstaller 友好）。
执行标准《持续研发任务清单与制作指引》在另一个工作副本里，**不在本分支**，
因此这里不引用它——凡本文引用的都能在本分支内复核。

所以"作品库到底装什么"属产品决策。本任务按下面这条最小定义落地，并在此写明假设：

> **作品库把每一次落盘的成图变成一条可检索的记录，跨批次地按提示词、种子、
> 标签、确认状态、批次或模型找图，并能收藏与整理。**

## 2. 最重要的一个设计决定：它是索引，不是第二个真相源

成图的事实早就存在——一份批次的复核文档（`<数据目录>/reviews/<run_id>.json`）
加磁盘上的 PNG。作品库**只读它们**，把结果派生成一张宽表：

| 做法 | 为什么不 |
|---|---|
| 让作品库成为成图元数据的权威 | 立刻出现"两个库说不一样"的问题：复核文档写的种子、报告写的种子、库里写的种子，三份都要维护，谁错了都难查 |
| 只存"用户自己加的"东西（标签/收藏），元数据每次现读 | 就没有索引的价值了——跨 43 个批次、1500+ 条记录做关键词检索要读十几 MB JSON |

因此边界很硬：

- **派生列**（标题、提示词、种子、模型、路径、尺寸、字节数、确认状态…）
  每次同步都从来源重写，来源永远是权威；
- **用户列**（`favorite`、标签、`deleted_at`）**任何同步都不许动**，
  因为它们推不出来。这条用白名单在 SQL 层强制（`_SYNCED_COLUMNS`），
  不是靠"记得别写"。

## 3. 表结构

单文件 `<数据目录>/library.db`，`meta.schema_version = 1`。

| 表 | 内容 |
|---|---|
| `works` | 一条记录＝一个批次里的一个编号（`work_id = "<run_id>:<编号四位>"`）。派生列 + `favorite` + `deleted_at` + `indexed_at`/`updated_at` |
| `work_tags` | `(work_id, tag)` 主键，天然去重 |
| `runs` | 每个批次的合计（总数/完成/失败/输出目录） |

`work_id` 取「批次 + 编号」而**不是文件路径**：重做会换掉磁盘上的文件，
标签和收藏必须留在同一条记录上。

`indexed_at` 只在插入时写：它记的是"第一次进库"，后来的同步不许把它改成现在
（`_INSERT_ONLY_COLUMNS`）。

编号必须是整数才会入库：非整数编号没有稳定身份，`work_id_for` 会把它们全折到
`...:0000`，后一条就会悄悄覆盖前一条。现在这类条目计 `skipped`，宁可少一条也不张冠李戴。

### 输出目录为什么可能是空的

`runs.output_dir` / `works.output_dir` 来自复核文档，而**复核存储从不写这个字段**，
所以最初每条记录的输出目录都是空串。现在由应用层在同步时补上**本次批次**的
`config.output_dir`（runner 状态里还留着）。重启后从磁盘恢复的批次没有这个信息，
如实留空，不拿旧设置去猜——这一点也写在第 11 节。

## 4. 真机上撞到、并且修掉的问题（一）：默认排序

**默认排序把"成图已经不在原位"的记录排到了最前面。**

第一版 `newest`/`oldest` 的排序键是
`COALESCE(mtime_ns, indexed_at*1e9)`——看起来等价，其实是错的：
一批"全失败"的批次没有文件，于是每条都拿到"刚刚入库"的时间戳，
集体冒到用户真正拥有的作品之上。真机回填时 `?limit=50` 返回的前 50 条
**一条可用成图都没有**，抓了个正着。

修法是把排序键落到**图片自己的时间**上，并让没有文件的记录排在后面：

```sql
-- newest
(mtime_ns > 0) DESC, mtime_ns DESC, run_id DESC, item_index DESC
-- oldest
(mtime_ns > 0) DESC, mtime_ns ASC, run_id ASC, item_index ASC
```

回归测试 `test_newest_and_oldest_order_by_the_image_and_push_missing_files_last`
钉住这条：有图两两按 mtime 排，没图的一律最后。

## 5. 真机上撞到、并且修掉的问题（二）：库打不开会让程序打不开

`Application` 在**模块级**构造 `LibraryStore`，而 `_prepare()` 只兜住了第一次失败。
损坏文件挪不走时（Windows 上文件被占用、目录只读、路径的父级不是目录），
第二次建表会把 `sqlite3.DatabaseError` / `OSError` 抛穿构造器——一个可有可无的
派生索引，代价是**整个程序打不开**。

现在两次失败都降级：`available = False`、原因写进 `last_warning`，之后任何操作抛
`LibraryUnavailable`，路由返回 **503**（不是 400：库不可用不该伪装成"你请求错了"）。
审图与成图流程完全不依赖作品库，因此照常工作。

## 6. 删除是墓碑，不是删行

`deleted_at` 落在行上，`DELETE` 语句一次都不出现：

- 重新索引**不能**让已移除的记录复活（与设置存储同一套纪律）；
- 用户可以「显示已移除」把它恢复；
- **移除记录不动磁盘上的成图**。这是作品库操作，不是删作品——
  UI 的确认文案和 `docs` 都写明这一点，因为它最容易被误解成"删图"。

## 7. 读图的安全边界

`/api/library/preview` 与 `/api/library/image` **只接受 `work_id`**（预览多一个 `size`）：

- 路径由服务端从库里取，客户端指定不了任何文件；
- **白名单之外的查询参数一律 400**。第一版是"忽略"而不是"拒绝"，于是
  `?work_id=X&path=Y` 会正常返回——"只认 `work_id`"这句话在实现上并不成立；
- 未知 `work_id`、记录没有成图、成图已被挪走 → 400 且说明原因；
- **取到的文件还必须是图片**：扩展名要在白名单内，且必须能被图像库解码。
  没有这道闸，一条 `copied_to` 指向文本文件的记录就成了"按记录读任意文件"的口子；
- 预览走既有缩略图缓存（`ResultReviewStore.ensure_thumbnail`），原图返回未改动的字节；
- 读图按 `work_id` 取，**不过滤墓碑**：用户在「显示已移除」里看到的卡片仍然要能显示缩略图。
  移除的语义是"从默认列表消失"，不是"图取不到"——要取不到，得动磁盘上的图。

**没做到的（如实写明）**：端点不校验文件是否落在某个"输出根目录"内。
输出目录由用户任意配置、重启后恢复的批次又不知道自己原来的输出目录，
硬套一个根目录会把这些真实的图变成读不出来。因此边界是"只认图片 + 必须可解码"，
而不是"只认某个目录"。

## 8. 端点

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/library` | 检索：`q`／`run_id`／`review_status`／`tag`／`favorite`／`model`／`include_deleted`／`sort`／`limit`／`offset`，返回一页 + `facets`（状态、标签、批次）+ `stats` + `sorts`（排序键→中文标签）+ `available` |
| GET | `/api/library/preview?work_id=&size=` | 缩略图（JPEG） |
| GET | `/api/library/image?work_id=` | 原图 |
| POST | `/api/library/favorite` | 收藏／取消 |
| POST | `/api/library/tags` | 给 `tags` 数组＝整体替换；给 `tag`±`action`＝单条增删 |
| POST | `/api/library/delete` | 从作品库移除（墓碑） |
| POST | `/api/library/restore` | 恢复 |
| POST | `/api/library/reindex` | 从全部复核文档重建索引（可重入） |
| POST | `/api/library/maintain` | `vacuum`／`clear-index`（清派生行，保留收藏、标签与墓碑） |

全部写路由进 `WRITE_ROUTES`，因此受既有编辑租约保护。
库不可用时读路由与写路由都返回 503，并带 `library_unavailable: true`。

## 10. 独立审查发现与处理

对本分支做过一轮只读独立审查（规范 / 规格两条轨道），结论**无 HIGH / P1**。
除了第 4、5 节的两个问题与第 9 节的排序标签，逐条处理如下：

| 发现 | 级别 | 处理 |
|---|---|---|
| 读图端点不校验文件是否真是图片 | MEDIUM | 扩展名白名单 + 必须可解码；回归测试覆盖 `.txt` 与伪装成 `.png` 的文本 |
| `output_dir` 恒为空 | MEDIUM | 见第 3 节末 |
| `?path=` 一律 400 的声明不成立 | LOW | 见第 7 节 |
| `clear_index` 留下孤儿标签；两个标签计数口径不一致 | LOW | 清索引时连带删掉被清行的标签；`stats.tags` 与 `facets.tags` 同样只统计存活记录 |
| 非整数编号塌缩导致覆盖 | LOW | 见第 3 节末 |
| 回传本机数据目录绝对路径 | LOW | 从载荷里去掉，只留字节数 |

审查者明确列为"已核查、未发现问题"的：SQL 注入与 `LIKE` 转义、分页钳制与整数溢出、
SQLite 连接生命周期与 Windows 文件锁、白名单防覆盖、`work_id` 身份稳定性、
写路由的租约保护、`core.py` 零改动。

## 12. 已知限制

- 索引的刷新时机是"读复核页"或"点重建"；软件不在运行时产生的成图要再点一次重建。
- `clear-index` 会清掉派生行，但**不会**清掉收藏、标签与墓碑——这是有意的，代价是
  一批被收藏或已移除的记录会长期占位。
- **重启后恢复的批次没有输出目录**：复核文档不记它，库也不去猜，如实留空。
- 读图端点只做"是图片 + 可解码"，不做"必须在某个根目录下"，理由见第 7 节。
- 缩略图缓存沿用审图板那一份（`reviews/thumbs`），作品库不另建缓存目录。
- 每次结果推送都会同步一遍当前批次（内容不变也照写，幂等但有写盘开销）；
  批次条数不多时可以接受，没有做"只在变化时同步"的短路。
- 相似图检索（按图像内容找同款）没有做，本任务只做元数据维度。
- 全量测试有 1 项偶发报错（`test_live_sync` 的实例文件往返，Windows 临时目录时序），与本任务改动无关：该测试与实例锁实现（`comfybatch_hub.py`）本分支未改动，单独运行与后续多次全量运行均通过。
