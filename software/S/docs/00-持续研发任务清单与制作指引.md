# S / ComfyBatch 持续研发任务清单与制作指引

本文件规定研发状态、完成标准和代码冲突处理方法。GitHub Issue #2 是实时进度看板；本文件是执行标准。每次开始、交接、合并或部署时，都要核对二者。

## 状态标记

| 标记 | 状态 | 使用条件 |
|---|---|---|
| ✅ | 已完成 | 代码、测试、审查、PR 合并、打包、桌面部署和验收记录全部完成 |
| 🟡 | 进行中 | 已开始且仍有明确的下一步；必须列出未完成项 |
| 🟠 | 隔离完成 | 因代码冲突已在独立分支完成和测试，但尚未进入正式软件 |
| ⛔ | 阻塞 | 缺少用户决定、依赖、权限或安全条件；必须写明解除条件 |
| ⬜ | 待开始 | 尚未进入实施 |

状态只按事实更新。代码写完但尚未合并、部署或验收的项目保持 🟡；隔离分支完成的冲突功能标记 🟠，不能标记 ✅。

## 每项制作流程

1. **建立边界**：从 GitHub Issue #2 选择一个原子里程碑，写清输入、输出、兼容性和验收条件。完成条件：范围可以由一个独立 PR 交付。
2. **检查现场**：读取 `AGENTS.md`、本文件、`HANDOFF.md`、当前分支及相对 `main` 的完整差异。完成条件：每个已有改动都已判断为相关、无关或冲突。
3. **建立分支**：使用独立的 `handoff/local-s-*` 分支；保留用户已有改动。完成条件：分支基点和工作树状态已记录。
4. **先验收后实现**：为新行为和风险边界补测试，再完成最小实现。完成条件：新增测试能证明需求成立，相关旧测试无回归。
5. **执行发布闸门**：Python 编译、前端词法检查、全量测试、公开内容扫描全部通过。完成条件：结果和跳过原因准确写入 `HANDOFF.md`。
6. **独立审查**：分别检查规范符合性和需求符合性；云端 GPT 对公开 PR 复审。完成条件：没有未解决的 HIGH/P1 问题。
7. **合并与构建**：合并独立 PR，以合并后的源码构建候选包并记录大小、SHA-256 和签名状态。完成条件：候选包来自已审查源码，仓库不含 EXE、日志、用户设置或密钥。
8. **桌面发布**：先备份现用 EXE，再停止精确识别的父子进程、替换、启动并在 Edge 验收。完成条件：版本、页面资源、核心功能和重复启动均通过，备份可恢复。
9. **收口**：更新本文件的状态快照、GitHub Issue #2 和验收记录。只有全部完成条件成立时，项目才从 🟡 改为 ✅。

## 完成标准（Definition of Done）

一项需求只有同时满足以下条件才能标记 ✅：

- 需求与兼容性范围已记录；
- 实现位于独立分支，没有夹带无关改动；
- 新增测试覆盖正常路径、失败路径和关键安全边界；
- Python 编译、前端词法检查和全量测试通过；
- 公开内容扫描不含密钥、私人路径、私人文件名、日志、构建目录和二进制产物；
- 独立审查无遗留 HIGH/P1；
- PR 已合并；
- 候选包已记录 SHA-256，且来源与已合并代码一致；
- 桌面已备份、部署并通过 Edge 与核心功能验收；
- `HANDOFF.md`、本清单和 GitHub Issue #2 已同步。

## 代码冲突隔离流程

发现同一文件或同一行为同时存在不兼容改动时，执行以下流程：

1. **停止集成**：正式分支、发布候选和桌面软件保持原状，先标记 ⛔“冲突待隔离”。
2. **制作备份**：把冲突文件、未提交差异、当前分支名和基点提交号保存到 `run/backups/conflicts/<时间戳>/`；该目录不得提交到公开仓库。
3. **建立隔离分支**：从明确记录的基点创建 `conflict/<需求编号>-<名称>` 分支或独立 worktree，不覆盖原工作树。
4. **独立制作**：在隔离分支完成冲突功能及测试，保留与正式代码的适配接口；不复制到正式分支，不参与正式 EXE 构建，不部署到桌面。
5. **记录结果**：在 GitHub Issue #2 标记 🟠，记录隔离分支、冲突文件、测试结果、备份位置和待决定的合并方案。
6. **专门集成**：冲突解决后另开集成 PR，重新执行全量测试、独立审查、构建和桌面验收；完成前保持 🟠。

冲突功能的“制作完成”和“进入软件”是两个独立状态。隔离完成只证明功能可用，不代表已经授权或适合进入正式版本。
