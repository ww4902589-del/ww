## 四、性能与行为对比

| 项目 | V2.13 | V2.14 |
|---|---|---|
| 缺失放大模型 | 提交后才由 ComfyUI 拒绝，正文丢失 | 预检阶段拦下，给出本机候选 |
| 同一结构性错误 | 提交 45 次，全部只报 `HTTP Error 400: Bad Request` | 第 1 条即停，中文原因 + 节点 + 参数 + 候选 |
| 执行失败判定 | 空转 1800 秒后报超时 | 读 `status_str` 秒级判定 |
| 错误可见性 | 页面完全不渲染 `results[].error` | 每张卡片可展开问题块与原始报文 |
| 状态展示 | 失败项仍显示 `submitted` | 按实际结果记录 `completed / error` 与 `aborted` |

`same_seed` 重做的实测结果：两次重做产出的 PNG **像素完全一致**，内嵌 seed 均为
`240936572945266`，耗时约 2 秒——因为提交图与种子完全相同，ComfyUI 直接命中缓存。
这正是“同种子重做”的预期语义（用于判断某张图是否偶然）。

## 五、本轮运行中发现并修复的额外缺陷

除根因分析报告列出的 5 项之外，真实联调还暴露了 4 项，均已修复并补测试：

1. 三个审图接口重复读取请求正文 → 接口永久挂起（实测 600 秒无响应）。
2. 重做结束无条件把状态写成“已完成”，会覆盖正在运行的批次。
3. 重做结果文件名前缀被重复拼接一次。
4. `/api/status` 只返回审核计数而不含结果数组，审图看板永远空白。
5. 重做后未标记为“已替换”、未记录历史版本（重做的 `attempts` 是新列表，
   “尝试次数变多”不是可靠信号，改为以 `redo_mode` 为准）。

另外修正了页面上两处不准确的提示文案，以及一处 `renderReview` 读取了错误形状的响应。
