# 资源替换与种子：实现与实测

本文回答两个具体问题：**缺失的模型能不能在软件内替换**，以及**打回重做后种子是否固定**。
两个问题的答案都由真实运行验证，不是推断。

---

## 一、缺失模型可以在软件内替换

### 用法

1. 点「实际检查」。若工作流引用了本机没有的文件，预检会拦下并说明是哪个节点、哪个参数、
   当前值是什么。
2. 打开「生效检查与依赖」抽屉，每个“缺资源”问题下面会出现：
   - 一个候选项下拉框（候选来自 ComfyUI 的 `/models/{目录}` 真实清单，**不是猜的**）；
   - **「仅本次批次生效」**：只在本次批次里用，关掉页面即失效；
   - **「保存为永久规则」**：写入 `resource_rules/resource_rules.json`，重启后仍生效。
3. 抽屉底部还有「打开模型目录」，按 7 个模型目录分别列出并可直接在资源管理器里打开，
   方便你选择“放文件”而不是“改规则”。
4. 已保存的规则列在抽屉里，可以逐条删除——替换不是单向门。

### 实测（真实 ComfyUI，真实工作流）

```
=== 1. 预检（应被拦下）===
 status 400 | 节点 11（UpscaleModelLoader）引用的文件「OmniSR_X4_DIV2K.safetensors」
                不在当前 ComfyUI 的资源清单中。

=== 2. 抽屉里的替换上下文 ===
 fingerprint: 0a0261f8ea0f
 upscale_candidates: ['RealESRGAN_x4plus_anime_6B.pth']
 model_directories keys: ['upscale_models','loras','checkpoints','diffusion_models',
                          'vae','text_encoders','unet']
 可替换问题: 节点 11 model_name | 候选 ['RealESRGAN_x4plus_anime_6B.pth']

=== 3. 在软件内保存永久替换规则 ===
 status 200 | 规则已写入（含工作流指纹 0a0261f8ea0f）

=== 4. 不传任何参数再预检（规则自动生效）===
 status 200 | ready: True
 节点11 model_name: source='user_replaced' value='RealESRGAN_x4plus_anime_6B.pth'
 replacements: [('11','model_name','RealESRGAN_x4plus_anime_6B.pth','用户在软件内替换')]
```

第 4 步是关键：**没有再传任何参数**，规则自动生效，且审计明确标出来源是
「用户在软件内替换」——所以这个值是工作流要的还是你改的，任何时候都能回答。

### 三条“不静默替换”的保证

1. 规则只能由你在界面里点选候选后创建，代码里没有任何自动匹配或模糊替换逻辑。
2. 编译时该输入被标记为新的来源 `user_replaced`，与 `override`（软件按配置重算）区分。
3. 审计单独输出 `replacements` 列表，抽屉的“生效参数”表因此会把替换显示出来。

### 规则什么时候会失效（重要）

规则以 **`工作流指纹 + 节点编号 + 参数名`** 为键。指纹进键是刻意的：工作流文件一改，
节点编号的含义可能就变了，旧规则不该继续悄悄生效。

但“指纹”用的是**结构性指纹**，不是整个文件的哈希。整个文件的哈希太脆弱——

| 你对工作流做的改动 | 整个文件哈希 | 结构性指纹（现在用的） |
|---|---|---|
| 在画布上拖动节点 | 变 → 规则失效 | **不变 → 规则继续有效** |
| 改节点标题、尺寸、颜色 | 变 → 规则失效 | **不变 → 规则继续有效** |
| 只是重新保存 / 重新导出 | 可能变 | **不变 → 规则继续有效** |
| 改一个参数值（如采样步数） | 变 | 变 → 规则暂停，并给出提示 |
| 静音/启用一个节点 | 变 | 变 → 规则暂停，并给出提示 |
| 增删节点、改连线 | 变 | 变 → 规则暂停，并给出提示 |
| 只改文件名（内容不变） | 不变 | 不变 → 规则继续有效 |

结构性指纹只取影响编译的部分：节点的 id、类型、静音状态、控件值，以及连线拓扑
（按“源节点/槽位 → 目标节点/槽位”记，不按连线编号，因为重新导出时连线编号会被重排）。

### 规则不会“悄悄失效”

如果工作流真的改到结构性指纹变了，旧规则会被**识别出来并提示**，而不是消失：

- 「实际生效检查」里出现提示：*“这个工作流文件改动过了，之前保存的 1 条替换规则已暂停生效
  （节点 11 的 model_name）。如果节点编号仍然对应，可在「生效检查与依赖」里点
  「沿用旧替换规则」重新启用。”*
- 抽屉里把这些规则列在「暂停生效」区，并给一个 **「沿用旧替换规则」** 按钮，一键挪到当前指纹。

为什么不自动沿用：工作流结构变了，同一个节点编号可能已经指向别的节点，
自动套用等于替你做了一个你没确认的决定。所以这里只提示、只提供一键沿用，绝不自动生效。

（这一点是被你追问后才做对的。最初的实现用的是整个文件哈希，实测发现
**仅仅在画布上拖动一个节点**就会让规则失效——这太脆弱了。）

### 作用域

| 作用域 | 存放位置 | 生命周期 |
|---|---|---|
| 仅本次批次 | 页面内存 → `config.resource_overrides` | 关闭页面即失效 |
| 永久规则 | 服务端 `resource_rules.json` | 重启后仍生效，可删除 |

合并时以“本次批次的显式选择”优先，两者都不覆盖你在别处显式指定的值。

## 二、重做后种子是否固定：取决于你选哪种重做

**结论：只有「同种子重做」固定种子；其余三种都会换新随机种子。**

| 重做方式 | 种子 | 做法 |
|---|---|---|
| `same_seed` 同种子 | **固定不变** | 直接重发上一次的提交图（`deepcopy`），种子已是具体整数 |
| `new_seed` 换种子 | **重新随机** | 重新编译 |
| `edited_prompt` 改提示词 | **重新随机** | 重新编译 |
| `reupscale_only` 仅重做放大 | **重新随机** | 重新编译，以上次输出作为输入图片 |

另外可以直接给某次重做**指定种子**（界面与接口都支持），用于“只变种子、其它全不变”。

### 实测（真实 ComfyUI，真实工作流，批次固定 seed=123456）

```
### 1. 首次生成，批次指定 seed=123456
    种子: {'19.seed': 123456, '20.seed': 123457} | 001-种子验证2_00001_.png

### 2. same_seed 重做
    种子: {'19.seed': 123456, '20.seed': 123457} | 001-redo-same_seed-143008_00001_.png

### 3. new_seed 重做
    种子: {'19.seed': 402540681792910, '20.seed': 490386970428935} | ...

### 4. 显式钉种子重做 seed=777
    种子: {'19.seed': 777, '20.seed': 778} | ...

### 5. 结论
    same_seed 与首次一致            : True
    new_seed 与 same_seed 不同      : True
    pin777 写入提交图               : True
    版本记录 attempts/history       : 4 / 3

    像素对比（3168×1776）：
      首次 vs same_seed 完全相同 : True
      首次 vs new_seed  不同     : True
      首次 vs pin777    不同     : True
```

- `same_seed` 的种子与首次**完全相同**，像素也**逐点相同** → 真正的“复现”。
- `new_seed` 的种子是新的随机值，像素不同 → 真正的“换一张”。
- 种子会按节点偏移 1（这里是 `19.seed=777`、`20.seed=778`），
  避免一个工作流里多个采样器被喂同一个种子而产生相关性。
- 版本记录 `attempts 4 / history 3`：1 次首生成 + 3 次重做 = 4 次尝试，
  3 个被替换的旧版本保留在历史里。

### 页面上能看到种子

每张图卡片显示它**真实的提交种子**（从编译后的提交图里取出，不是界面上的意图值），
例如 `19.seed = 123456`。所以你可以随时核对某张图是用哪个种子生成的，再决定要不要复现。

### 提交种子不等于实际种子（V2.21 起）

上面那句只到"提交"为止。提交进 ComfyUI 的值，和这张图**真正用的**值，是两回事：
工作流里可能还有一层节点会改种子，历史也可能被清掉。所以从 V2.21 起分三个概念：

| 概念 | 含义 | 权威来源 |
|---|---|---|
| **提交种子** | 我们请求 ComfyUI 用的值 | 编译后的提交图 |
| **实际种子** | 这张图真正用的值 | 成图 PNG 自己内嵌的提示；读不到才退回 `/history/<id>` |
| **未核对** | 两处都读不到 | —— 显式为第三态 |

为什么权威来源是成图而不是 `/history`：历史会被清理，成图不会。ComfyUI 把**实际执行**
的提示写进 PNG 的 `prompt` 文本块，所以这张图自己就是最硬的证据。

"未核对"必须单独存在。**读不到 ≠ 没生效**——把两者混为一谈，会让每一张旧图、
每一个被改过元数据的文件都背上一个假罪名。所以读不到时 `effective` 是 `None`，
不是 `False`，卡片上写「种子（未核对）」。

卡片因此可能显示：

- `实际种子 20.seed = 424242 ← 图片内嵌提示`（读到了，附来源）
- `种子（未核对）`（两处都读不到，不判罪）
- 提交值与实际值不一致时，两张都列出来并标红差异，复用按钮填的是**实际**种子，
  这样"复现这一张"复现的是它真正的样子。

批次报告里对应多出 `real_values`、`real_duplicates`、`mismatched`、`unverified_indexes`：
前两个回答"哪几张其实是同一张"，第三个回答"哪几张的种子被改过"，最后一个只统计
**报告为完成、但读不到种子**的图。

### 种子固定不了的工作流，预检就说明白

有一种工作流固定种子是**无效**的：种子由一个**上游节点**提供，而那个上游节点自己
没有可写的种子参数。这时无论界面给什么值，每次出图都是随机的。

旧实现只会在"提交值恰好等于上次"时提示「固定种子未生效」——而随机工作流永远不会
相等，所以永远不会提示，用户会以为种子固定住了。

现在预检阶段就把全图种子分成三类如实报告：

| 分类 | 含义 |
|---|---|
| `pinnable` | 有具体整数种子、可以直接写死的节点，如 `{"20.seed": -1}` |
| `linked` | 种子来自上游连线，会跟着上游走，如 `13.seed ← 20 Seed (rgthree)` |
| `uncontrollable` | 没有任何可写种子的上游，固定种子对它**无效** |

`linked` 里还会带上上游节点自己**能不能被固定**（`controllable`）。判断这个必须看
**全图**（含静音分支）——生产工作流常把种子节点放在静音分支里，只看当前分支会误报
成"不可控"。只要有一个节点不可控，预检就给出直白告警：

> 该工作流的种子由上游节点提供（3.seed ← 2 PrimitiveInt），上游节点自身也没有可写的
> 种子参数：固定种子不会生效，每次都会随机

真相栏也加了一行「种子」，在还没出图时就回答"这个工作流允许我固定哪些种子"。

### 顺带说明一个事实

`same_seed` 重做通常只需几秒，而 `new_seed` 需要完整重跑（实测约 190 秒）。
因为提交图和种子完全相同时，ComfyUI 会直接命中缓存。这不是偷懒，正是“同种子”应有的效果。

## 三、这一轮修掉的三个种子相关缺陷

实现过程中真实运行暴露了三个缺陷，都已修复并补了回归测试：

| 缺陷 | 症状 | 原因 |
|---|---|---|
| 批次固定种子会锁死 `new_seed` | 选了“换种子”，产出的图与上一张**逐点相同**，重做只花 5 秒（缓存命中） | 固定种子存在 `config` 上，重做重新编译时又被写回。现在 `new_seed` 会释放批次种子 |
| 显式指定种子不生效 | 传 `seed=777`，提交图里仍是旧种子 | 接口层没有把 `seed` 转发给重做逻辑 |
| 尝试次数与历史版本无限增长 | 一次重做后记录变成 `attempts 162 / history 161` | `/api/status` 每次轮询都会 ingest，而带 `redo_mode` 的结果被反复判定为“新版本”。现在按 `prompt_id` 判重，重复 ingest 不再累加 |

这三个都是“静态测试与合成数据看不见、只有真实运行才会暴露”的问题。
第一和第二个尤其隐蔽：表面上重做“成功”了，产出的却是同一张图。

## 四、真实种子的实测（V2.21）

用真实 ComfyUI、真实工作流（本机 Krea2 生图流 + SeedVR2 放大），
提示词取自已导入的中文提示词包，比对**像素**而不是文字：

```
== 批 1：固定种子 424242
  提交={'20.seed': 424242} 报告实际={'20.seed': 424242}
  图片内嵌={'20.seed': 424242} 生效=True 像素=42b3556c938b275e
== 批 2：同一种子 424242 再跑一次
  提交={'20.seed': 424242} 报告实际={'20.seed': 424242}
  图片内嵌={'20.seed': 424242} 生效=True 像素=42b3556c938b275e
== 批 3：固定种子 999999
  提交={'20.seed': 999999} 报告实际={'20.seed': 999999}
  图片内嵌={'20.seed': 999999} 生效=True 像素=c77af964e4d1b3f1

同一固定种子重跑 → 像素相同
换固定种子重跑   → 像素不同
验收：通过
```

三点值得记下来：

1. **三方一致**：提交值、报告里的实际值、成图自己内嵌的值，三批全部相等。种子的
   读取路径是通的，不是把提交值原样抄了一遍。
2. **像素是硬证据**：同种子两次 `42b3556c938b275e` 逐点相同，换种子 `c77af964e4d1b3f1`
   不同。这说明"固定"在真实生成里成立，而不只是我们把数字写进了图。
3. **这个工作流是 `linked` 型**：`20.seed` 可固定，`21.noise_seed` 和 `13.seed` 由它飞线
   驱动。所以只写一个节点就把两个采样器都定住了——种子偏移逻辑保证它们不会撞成同一个值。

### 一条如实记录的既有语义：API 格式的工作流不随机化种子

UI 格式（`{"nodes": [...]}`）的工作流会被写入随机种子；**API 格式
（`{node_id: {class_type, inputs}}`）的工作流按原样提交**，只覆盖 loader、分辨率和保存
前缀。也就是说，API 工作流的种子不会被软件随机化。

这是既有约定，不是这一轮引入的行为，所以没有改它——只补了一项测试把这个语义固定下来，
并让 `real_duplicates` 如实把它暴露出来（同一批里多张图种子相同就会列出来）。若以后要
改，那是一个独立需求。
