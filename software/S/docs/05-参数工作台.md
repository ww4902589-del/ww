# 参数工作台（P2）

计划书把这套软件定义为「可检查、可调整、可调试的 ComfyUI 工作台」，而不是
「固定字段批量提交器」。这一轮补上的就是这中间最大的一块：**在页面里改参数，
并让改动真正写进提交给 ComfyUI 的工作流**。

在此之前，页面上只能调画幅、百万像素、负面提示词和重试次数；采样步数、CFG、降噪、
放大倍数、分块参数一个都改不了。

---

## 一、一个声明，四处生效

参数只在 `src/comfybatch_params.py` 的 `PARAMS` 里声明一次。这一份声明同时决定：

| 用途 | 由谁读取 |
|---|---|
| 页面上渲染什么控件（标签、类型、上下限、候选） | `registry_payload()` → `/api/params` |
| 输入值合不合法（含枚举候选、值域） | `resolve()`，对照实时 `object_info` |
| 写到提交图的哪个节点的哪个输入 | `ParamSpec.targets` + `apply_params()` |
| 在「实际生效参数」表里怎么解释自己 | 来源标记 `param`（中文「参数工作台」） |

这样做的理由很直接：如果界面、校验、写入是三份各自维护的清单，它们迟早会漂移，
而漂移的表现是「页面显示了某个值，但它从没到过 ComfyUI」——最难查的一类问题。
加一个参数现在是加一条声明，不是改四个地方。

## 二、26 个参数

### 常用参数（10）

初始宽度、初始高度、每任务张数、采样步数、CFG、降噪、放大倍数、放大模型、
分块尺寸、潜空间放大倍数。

### 高级参数（16）

一采步数、二采步数、采样器、调度器、起始步、结束步、是否加噪、保留残余噪声、
分块顺序、遮罩模糊、分块边距、接缝模式、接缝降噪、接缝宽度、统一分块、分块解码。

枚举类参数的候选**不是写死的**，而是从当前 ComfyUI 的 `object_info` 读取。
实测本机采样器候选有 44 个（`euler`、`euler_cfg_pp`、`euler_ancestral` …），
页面上就是这 44 项的下拉框。

## 三、一采 / 二采是怎么区分的

「一采步数」和「二采步数」必须有明确的含义，否则不如不给。节点编号没有执行顺序含义，
所以顺序是从**潜空间链路**推出来的：

判定规则：某个采样器的 `latent_image` 沿上游走，如果能走到另一个采样器，那它就是后一采。

以真实的极清工作流 `save:1` 分支为例：

```
16 EmptyLatentImage ──► 21 KSamplerAdvanced ──► 22 LatentUpscaleBy ──► 13 KSampler
                         （一采）                  （潜空间放大）        （二采）
```

实测结果：`{'21': 1, '13': 2}` —— 21 是一采，13 是二采。

注意 21 是 `KSamplerAdvanced`、13 是 `KSampler`，光看节点类型或编号都会判错，
只有看链路才对。设 `steps_stage1=12, steps_stage2=30` 的实测结果：
节点 21 的 `steps` = 12，节点 13 的 `steps` = 30。

## 四、四种作用范围

| 作用范围 | 存到哪里 | 生命周期 |
|---|---|---|
| 整个批次 | 页面内存 → `config.params` | 关闭页面即失效 |
| 保存为该工作流默认值 | 服务端 `workflow_params.json`，键为工作流指纹 | 重启后仍生效，可清空 |
| 仅选中的任务 | 任务项的 `metadata.generation.params` | 随提示词一起走 |
| （工作流自身） | 不动 | 留空即沿用工作流的值 |

合并优先级：**任务级 > 批次级 > 工作流默认值 > 工作流自身的值**。
页面上每个字段都会标出当前值来自哪一层（「批次值」/「默认值」角标）。

任务级参数和模型、风格一样挂在任务项上，所以导出的提示词合集自带这些设定。

## 五、不会「改了却没生效」

参数层的三种情况都会明确说出来，而不是安静地什么都没发生：

1. **越界或类型错误** —— 阻断。例如 `steps=99999` 会报
   「采样步数 不能大于 200（收到 99999）」，且**整批参数都不写入**，
   不会出现「一半生效一半没生效」。
2. **参数名拼错** —— 警告。例如 `defualt` 会报「参数工作台里没有名为「defualt」的参数，
   已忽略以免改写错误的节点输入」。
3. **目标输入被连线驱动** —— 警告，并指出该改哪个参数。实测：

   > 「初始宽度」对应的输入（节点 16）是指向「ResolutionSelector」的连线，
   > 它的值由那个节点决定，所以这里改不了。
   > 修复：改用驱动它的那个节点的参数（例如尺寸由 ResolutionSelector 驱动时，
   > 请改「画幅」与「百万像素」）

   这一条很实用：这个工作流的宽高由 `ResolutionSelector` 决定，直接设「初始宽度」
   是无效的，必须改「画幅」和「百万像素」。不提示的话，用户只会觉得「设了没用」。

另外，**指向其他节点的连线永不被参数覆盖**。那属于工作流的连线逻辑，覆盖它等于
悄悄改掉工作流结构。

## 六、实测：参数真的到 ComfyUI 了吗

光看页面显示不算数，所以选了一个**结果可观测**的参数来验：放大倍数。

```
### 1. 读取参数工作台定义
    常用参数: base_width, base_height, batch_size, steps, cfg, denoise,
              upscale_by, upscale_model, tile_size, latent_upscale_by
    高级参数: steps_stage1, steps_stage2, sampler_name, scheduler, start_at_step,
              end_at_step, add_noise, return_with_leftover_noise, mode_type,
              mask_blur, tile_padding, seam_fix_mode, seam_fix_denoise,
              seam_fix_width, force_uniform_tiles, tiled_decode
    采样器候选: 44 个（来自实时 schema）

### 2. 保存工作流默认值：放大倍数 2.0 → 1.0
    已保存: {'upscale_by': 1.0, 'steps_stage1': 6}

### 3. 预检（刻意不传任何 params，默认值应自动生效）
    节点3  放大倍数: value=1.0  source=param  source_cn=参数工作台
    节点21 步数    : value=6    source=param  source_cn=参数工作台

### 4. 真实生成
    耗时: 69.05 秒

### 5. 结果对比
    最终尺寸: 1584×888        ← 改了放大倍数
    基线尺寸: 3168×1776       ← 未改时
    卡片显示: 1024×576 → 1584×888（×1.55）
    种子    : {'19.seed': 123456, '20.seed': 123457}

### 6. 清空工作流默认值后
    节点3 放大倍数回到 2.0（来源变回「本次运行覆盖」）
```

第 3 步是关键：**没有传任何参数**，工作流默认值自动生效，审计里明确标着来源是「参数工作台」。
第 5 步的输出尺寸从 3168×1776 变成 1584×888，说明这个值确实到了 ComfyUI 并改变了结果；
耗时也从约 196 秒降到 69 秒。第 6 步证明清空后能干净地回到原值。

## 七、这一轮修掉的两个缺陷

实现过程中真实运行暴露出来的，都已修复并补了回归测试：

| 缺陷 | 症状 | 原因 |
|---|---|---|
| 越界值被写进默认值 | 越界参数当场报了错，但下一次运行它又回来了 | 校验用了 `valid`，持久化却用了原始 `raw`。现在只存通过校验的部分 |
| 任意的 `/object_info` 响应都被当节点定义 | 网关返回非节点定义内容时，会生成一份只有一个条目的 schema，于是**所有真实节点都被报成「缺少节点」** | 新增 `NodeSchemaRegistry.looks_valid()`，要求响应确实是节点定义（每个值都是字典、且多数带 `input`）；不合格就沿用缓存或旧 schema，而不是把好 schema 换成垃圾 |

第二个尤其值得记下来：坏 schema 比没有 schema 更糟，因为报错方向完全是误导的。
