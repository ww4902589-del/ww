# 成图落盘与预览修复

> ⚠️ **后续修订（2026-09-19 20:20）**：本文第 2 条修复里"**只取文件名**（不再重建 ComfyUI 内部目录树）"
> 的做法**已被取代**。它把整个层级都删掉了，导致不同批次的同名图互相撞名。
> 现行行为见 [待决问题修改方案预设](15-待决问题修改方案预设.md) §1.1：
> **保留批次子目录 `<run>/`，只丢掉 App 命名的那一层 `ComfyBatch-V2`**。
> 下文保留原文以记录当时的判断。

本轮针对"图片的预览和存储也是个问题"做的修复。两个缺陷都是**用真实批次跑出来的**，
不是读代码猜的：一个让成图根本存不下来，一个让成图存下来之后看不动。

## 一、成图存不下来：`[WinError 3] 系统找不到指定的路径`

### 现象

批次跑完，ComfyUI 里明明有图，输出目录里却一张都没有，每条任务都是：

```
[执行失败] 任务失败；[WinError 3] 系统找不到指定的路径。
```

而且**批次不会停**。原来的实现里 `shutil.copy2` 抛的是普通 `OSError`，不是工作流级
`Problem`，所以止损逻辑看不见它——每条任务照常失败、照常往下走，最后报一个
`completed_with_errors`，看起来像"跑完了但有几张出错"，而不是"保存路径坏了"。

### 根因：ComfyUI 的两种上报形状

ComfyUI 通过两条不同的代码路径上报输出文件，它们对"目录归谁"的说法不一致：

| 形状 | `subfolder` | `filename` |
|---|---|---|
| websocket / `/history` | `"ComfyBatch-V2/9e707e3f"` | `"001-探针1_00001_.png"` |
| `/view` 系列 | `""` | `"ComfyBatch-V2/9e707e3f/001-探针1_00001_.png"` |

原来的代码无条件拼接：

```python
source = self.comfy_root / "output" / str(image.get("subfolder") or "") / str(image["filename"])
```

第二种形状下就得到 `output/a/b/a/b/x.png`——目录被写了两遍，文件当然不存在。
本机的真实 ComfyUI 输出目录印证了这个行为：

```
<ComfyUI目录>\output\
    Codex\ChuiMengDaoXiZhou\V01_00001.png      <- 前缀的目录真实存在，文件名是裸的
    Codex\ChuiMengDaoXiZhouV2\V01A_00001.png
```

### 修复

抽出 `resolve_output_source()`：把 `subfolder` 与 `filename` 都按路径分段拆开，
**`filename` 已经带着目录时以它为准**（因为它无论如何都相对输出根目录），
否则再拼接。无法判断时退回字面拼接，好让调用方拿到精确的"文件不存在"而不是一个错误的命中。

复制目标同时抽出 `copy_output_image()`，修掉两个附带缺陷：

- **目标路径不再重建 ComfyUI 的内部目录树。** ~~原来 `target = output_dir / filename`，
  前缀里带斜杠时会把 `ComfyBatch-V2/<run>/` 整棵树复制到用户选的输出目录里。
  现在只取文件名，这才是"输出目录"这个字段承诺的东西。~~
  **（已被 §1.1 取代）** 当时把整棵树都删了，但 `<run>/` 那一层正是把一批图组织成集合的东西；
  删掉之后不同批次的同名图会撞名。现行做法是**保留 `<run>/`，只丢掉 `ComfyBatch-V2` 那层**。
- **不再自己覆盖自己。** 用户如果把输出目录指向 ComfyUI 输出根目录之内，
  原来的写法会算出 `source == target`，`shutil.copy2` 抛 `SameFileError`。现在识别后直接返回。
- **重名不再互相覆盖。** 两条任务解析到同一个名字时依次取 `-v2`、`-v3`。

三处重复的复制代码（`_run`、`_redo_one`、`redo`）现在共用同一对函数。

### 验证

`tests/test_output_paths.py` 钉住两种形状、反斜杠、扁平文件名、自覆盖、重名，
以及两条端到端批次（每种形状一条）必须 `completed` 且**文件真的落盘**。
另外用真实 `BatchRunner` + 模拟 ComfyUI 跑过一批：3/3 落盘、0 错误、输出目录无多余子目录。

## 二、预览看不快：看板每次都拉全尺寸 PNG

### 现象

成图看板和画廊的每个 `<img>` 都直接指 `/api/image`，也就是**整张原图**。
一个 20 张的批次，光是打开第 6 阶段就要解码和传输数百 MB；
更糟的是 SSE 推送与轮询每次都会重渲染，于是又全部重拉一遍。

`ResultReviewStore.list_for_run()` 里 `entry["thumbnail"]` 实际上被硬编码成空字符串——
缩略图从来没有生成过，字段存在但没有意义。

### 修复

- **预览缓存**：新增 `ResultReviewStore.ensure_thumbnail()`，按源文件（路径 + 大小 + mtime）
  的哈希缓存一张最长边 512px 的 JPEG。放在应用数据目录，**故意不放在输出目录**——
  理由和确认记录一样：输出目录被移动或清空时预览不该跟着丢。
  源文件变了（重做换了一张）哈希就变了，缓存自然失效，不会拿旧图糊弄。
  缩略图生成失败（文件读不了）时**回退成源文件本身**，宁可大一点也不让页面上出现空图。
- **独立端点** `/api/preview`：与 `/api/image` 分工明确——`/api/image` 继续原样输出
  全尺寸原图给审图和下载用，`/api/preview` 负责缩略图，可以放心降采样和强缓存。
  两者共用同一份"这张图属于当前批次"的准入判断，越权路径照样 400。
- **缓存头**：`/api/image` 补上 `Cache-Control: private, max-age=604800`，
  重开查看器不再重下原图。
- **前端**：看板、结果卡、画廊统一改用 `/api/preview`；查看器先开 1600px 预览，
  点图再切原图（`toggleViewerFull`），不为了一张图先传几 MB。

### 效果

用真实噪声填充的 2048×2048 PNG（近似放大后的成图）实测：

| | 原图 | 预览 |
|---|---|---|
| 单张 | 12.02 MB | 68.6 KB |
| 4 张合计 | 48.08 MB | 274.8 KB |

**数据量下降 99.4%。** 20 张批次从 240 MB 降到 1.3 MB，且因为缓存只需拉一次。

## 三、顺带修掉的操作麻烦：打回重做要手打英文枚举值

原来 `reviewReject()` 弹**两次** `prompt()`：先输原因，再让用户把
`same_seed` / `new_seed` / `edited_prompt` / `reupscale_only` 之一原样敲进去。
敲错只回一句"不支持的重做方式：xxx"，既不告诉合法值也不告诉各是什么意思。

现在改成真正的对话框：

- **下拉选择重做方式**，每一项都带中文说明
  （"换种子重做（只换随机种子，重新抽一张）"），选项直接从服务端的 `redo_modes` 来，
  不会出现界面有、后端不认的值。
- 选中项的说明单独显示在下方，不用记。
- 原因用 `textarea`，可以换行、可以留空。
- `prompt()` 调用**全部清掉**（有测试数着数量）。
- 上一次运行的成图会被明确拒绝并说明原因（缺 bundle 和 config，重做不了），
  而不是点了之后报一个看不懂的错。

「记录问题」同样换成对话框；键盘审图的 `N` 键走同一个入口，两种方式行为一致。

## 四、查看器「看原图」切不回去

改完预览之后，用无头 DOM 跑真实 `app.js` 才发现的一个连带缺陷。

`toggleViewerFull()` 切回预览时，用 `activeIndex` 反查当前行：

```js
const row=(reviewState.results||[]).find(x=>x.index===activeIndex);
```

但 `activeIndex` **只有 `setActive()` 会写**，而画廊网格里的 `<img>` 直接绑的是
`openViewer(...)`，结果卡的按钮又都 `stopPropagation()` 了。也就是说从网格或卡片
点开大图时 `activeIndex` 还是 `-1`：第一次点图能切到原图，再点一次切回来就变成
`/api/preview?path=&size=1600`——空白路径，图直接裂掉。

修法是让查看器自己记住展示的是哪一张（新增 `viewerIndex`，在 `openViewer()` 里赋值），
不再依赖 `setActive()` 有没有先跑过。入口之间互不依赖，这个 bug 才不会在别的路径上复现。

## 五、模型名形状不一致导致"明明装着却说不兼容"（本轮一并修掉）

跑端到端探针时撞到的第二条**同源缺陷**：和第一条落盘问题一模一样——
两处用不同形状描述同一个东西，再用**字符串相等**去比。

### 现象

工作流清单里各工作流的 `current_model` 形状不统一：

```
▶▷krea2-图像编辑-整合流.json           current_model = "Krea2\\krea2_turbo_int8_convrot.safetensors"
▶▷krea2-图像编辑-整合流（有效修正版）   current_model = "krea2_turbo_int8_convrot.safetensors"
```

而 `/api/start` 的校验是裸字符串相等：

```python
if not any(item.get("value") == config.model for item in compatible):
    raise ValueError(f"模型“{config.model}”与所选工作流不兼容…")
```

`_models()` 给出的 `value` 是**相对模型根目录的路径**（`Krea2/krea2_turbo.safetensors`），
而 loader 节点里可能只写裸文件名。两者永不相等 —— 用户明明装着这个模型，
却被判"不兼容"，只能对着下拉框里一个能用的都没有干瞪眼。这就是"调整麻烦"的一部分。

### 修复

抽出**唯一**的归一化函数 `ResourceInventory.model_basename()` / `model_key()`，
`/` 与 `\` 都当分隔符（Windows 存的工作流带反斜杠），三处一起改用：

- `_workflow_model()` 返回裸文件名 → `current_model` 从此形状统一。
- `validate_start()` 按 `model_key` 比对，不再裸字符串相等。
- 顺带把 `compatible_models_for()` 拆出来（按 loader + family 过滤，
  **family 收窄后为空则回退到 loader 全表**，避免 `unknown` 家族把菜单清空）。

### 前端也上了同一份真相

`renderModels()` 原本**自己重写了一遍过滤逻辑**：

```js
inventory.models.filter(x=>(!loader||x.loader===loader)&&(!workflow.model_family||...))
```

这正是两边能漂移的原因。现在清单里每个工作流直接带 `compatible_models`
（由 `/api/start` 校验用的**同一个方法**算出），前端只做展示，
下拉项标签改用裸文件名（`basename()`，与 Python 侧同规则）——
文件夹是 loader 的事，不该泄进下拉框。

### 验证

新增 8 项测试，先写失败用例确认缺陷真实（3/5 失败），再修到全过：

```
Ran 352 tests ... OK (skipped=1)     # 344 -> 352
```

线上实测（真实 ComfyUI 清单）：

| 传入的 model | 结果 |
|---|---|
| 裸名 `krea2_turbo_int8_convrot.safetensors` | 通过模型匹配（仅剩负面提示词的无关告警） |
| 带目录 `Krea2/krea2_turbo_int8_convrot.safetensors` | 通过模型匹配 |
| 真的不存在 `definitely_not_installed.safetensors` | **仍然拒绝**："与所选工作流不兼容；请选择：krea2" |

最后一行是要点：放宽匹配**没有**变成橡皮图章，真正的错配照样拦得住
（`test_blocks_model_from_wrong_family_before_queueing` 仍在跑）。

### 端到端探针的环境限制（不影响结论）

`run/probe_e2e.py` 需要一台 ComfyUI，本机用的是 `run/fake_comfy.py` 这个替身。
替身只提供 fixture 里的 `/object_info`，**模型家族分类无法像真实 ComfyUI 那样
从装好的模型文件推断出来**，于是探针到不了"复制落盘"那一步。

这是探针环境的天花板，不是产品缺陷。**落盘修复的证据以单元测试为准**：

```

Ran 18 tests ... OK
```

其中两条走的是**真实 `BatchRunner` + 真实复制逻辑**，两种上报形状各一条，
断言成图确实躺在输出目录里、且没有多出子目录——这比 HTTP 探针更贴近出问题的那段代码。

替身已顺带改进：`/models/checkpoints` 现在从 `tests/fixtures/workflow_*.json` 里
**自动抓出所有被引用的模型文件名**（同时兼容 API 图与 UI 图的两种结构），
替身与工作流清单不会各自漂移。

## 验证用的无头 DOM 跑法

本环境的浏览器自动化通道在 `open` 上会无限阻塞（试过两次，都等到工具超时），
截图不可靠。改为 `run/check_review_ui.py`：把**真正被服务出去的 `app.js`**
用 `vm.createContext` 装进一个手写的 DOM 里，断言的是发布代码本身而不是它的截图，
比截图更接近真实，而且可重复。

```
node run/_dom_harness.js src/app.js run/_dom_harness.json
```

11 项全过，覆盖：对话框真的 `showModal()`、四个重做方式都有中文标签、
选中项的说明、`prompt()` 零调用、网格与结果卡都走 `/api/preview`、
查看器预览 ↔ 原图双向切换——**并断言切回来的 URL 里仍带着图片路径**，
正是这条断言钉住了第四节那个 `activeIndex` 缺陷——以及模型下拉框
（值保留服务端引用、标签用裸文件名，对应第五节）。

两个踩过的坑，值得留档：

1. **`vm.runInContext` 里顶层 `let` 不会出现在 sandbox 对象上，`var` 和函数声明会。**
   实测：`outside sees reviewState property: undefined` / `var leaks to global: 42`。
   所以要种状态必须走模块自己的入口 `renderReview(v)`；直接
   `sandbox.reviewState = {...}` 只会造一个模块读不到的影子，
   表现成"调用不报错但什么都不发生"——第一版 5/10 全卡在这。
2. **本沙箱禁止嵌套创建进程。** Python 里 `subprocess.run` 再拉起 Node 会静默失败
   （父进程直接死，连 `except` 都进不去），所以 `check_review_ui.py` 支持
   `--emit-only` 只生成 JS，Node 由调用方直接执行。
