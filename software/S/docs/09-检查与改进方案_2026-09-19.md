# S / ComfyBatch V2.18 检查与改进方案（2026-09-19）

本轮为**方案轮**：先给现状（带代码证据）→ 方案 → 落实方式，经确认后再动代码。
探查范围：`src/`（app.py 104K / core 164K / nodeschema 56K / params 24K / hub 8K / gateway 12K / index.html / app.js / app.css）、`docs/01~08`、`tests/`、`tools/acceptance/`、`<工作流目录>\` 10 个工作流、桌面 S.exe 与构建产物对照。

**版本基线**：页面标题与 `APP_VERSION` 均为 V2.18；桌面 `<桌面目录>\S.exe`（17,043,461 字节）与 `build/dist2/S.exe` 完全一致，即桌面版=最新构建。`<备用目录>\S.exe` 不存在。

## 1. 前后端功能对应性检查

**现状**：31 个 POST + 16 个 GET 端点，前端统一走 `api()` 封装；「页面显示值 == 提交值」有测试守卫（docs 08 §五，`tests/test_script_parses`、`InspectPayloadTests`）。总体对应良好，但发现 6 处缺口：

| # | 缺口 | 证据 | 定性 |
|---|---|---|---|
| A | 后端 `/api/review/redo` 接受 `seed`，前端 `submitReject` 不发送 | app.py:1712-1718 vs app.js:1517 | 并入第 7 项（种子） |
| B | `/api/restore-default-presets` + `/api/deleted-presets` 后端完整（墓碑式删除+按需恢复），前端无任何入口 | app.py:1442,1655-1662 | 已删预设无法从 UI 恢复 → 第 2 项 |
| C | `/api/params/clear` 后端可清除已保存的工作流参数默认值，前端 `clearWorkbench` 只清空本地未应用输入框 | app.py:1822-1827 vs app.js:957 | 已保存参数无法删除 → 第 2 项 |
| D | LoRA 档案只有 `save-lora-profile`，后端无删除端点 | app.py:1646 | 档案只进不出 → 第 2 项 |
| E | `/api/review/note` 前端未用（`submitNote` 走 `/api/review/confirm`） | app.js:1549 | 无害冗余，保留 |
| F | `/api/activate`、`/api/lease/renew`、`/api/resource/rules` 在 app.js 无直接调用 | — | 疑由托盘外壳/hub 层/inspect 载荷消化，落实时逐一核实后记录，不盲改 |

**落实方式**：A→第 7 项；B/C/D→第 2 项补 UI/端点；E 不动；F 出一段核实记录。

## 2. 「删除设定」补齐

**现状**：风格/LoRA 预设✓可删（阶段 2「删除预设」danger 按钮，墓碑式，重装不复活）；资源替换规则✓可逐条 forget；✗已保存参数默认值；✗LoRA 档案；✗恢复默认预设。

**方案**（三处小改）：
1. 预设命令条加「已删除／默认预设」入口：弹层列 `/api/deleted-presets`，按钮「恢复默认预设」→ `/api/restore-default-presets`；
2. 参数工作台 footer 加「清除已保存默认值…」→ `/api/params/clear`（先弹确认，列出将被清除的 key）；
3. 后端新增 `POST /api/delete-lora-profile`（仿 `delete_style_lora_preset` 的墓碑式），LoRA 档案列表每行加删除小按钮。

**落实方式**：`index.html` 阶段 2 两处 + LoRA 列模板；`app.js` 新函数 3 个；`comfybatch_v2_app.py` 加 1 个 handler；`tests/test_preset_store.py`/`test_app_routes.py` 补用例。墓碑纪律沿用：删除即登记、恢复必须显式。

## 3. 按钮显示是否明显

**现状**：主操作有常驻 sticky 栏（上一步/下一步/实际检查/「启动真实批次」primary），这个底子好。问题：
1. 「全部通过」批量动作是 secondary 样式、无数量提示、无确认——一键全过却毫不显眼也毫不设防；
2. 每卡片「通过/打回/记录问题」三动作在紧凑密度下会拥挤；
3. 危险操作（删除预设、取消剩余任务）缺统一二次确认。

**方案**：
- 「全部通过」改带徽标「全部通过 (N)」；N>5 时弹 confirm；
- 卡片三动作做固定色语义：通过=绿描边、打回=橙描边、记录=灰，紧凑模式下图标+短文字；
- 危险操作统一 `confirmDialog`（删除预设/清除参数/取消剩余任务/删除 LoRA 档案）；
- 运行中把 sticky 的「启动真实批次」替换为「运行中…暂停/取消」状态态，防止重复提交（后端状态机已兜底，这里只是体验）。

**落实方式**：`app.css` 按钮层级段 + `app.js` `confirmAllPending`/`renderReviewBoard`/`deletePreset`；`test_page_assets` 跑通即可。

## 4. 其他方向优化（顺带清单）

- 卡片「同种子」徽标 + 种子行「复用」按钮（第 7/8 项配套）；
- 批量重做进度显示（第 5 项配套，复用 progress bar + runText）；
- 报告 JSON 增加 seeds 频次统计（第 8 项配套）；
- 密度、种子模式存 localStorage 记忆；
- 输出目录帮助文案与 preflight 面板显示输出终值（第 9 项配套）；
- 低优先：`/api/review/note` 冗余端点清理。

## 5. 图片打回批量处理

**现状**：批量「通过」已支持（`indexes[]`）；**打回重做只能单张**——`/api/review/redo` 只收单个 `index`（app.py:1702），且 `runner.redo()` 每次调用起独立线程、状态为 running/starting 时拒绝第二次 redo（core:2245-2247）。前端审图卡片无勾选框。

**方案**：
- **后端**：`core` 新增 `redo_many(indexes, mode, *, prompt, note, seed)`——一次持锁校验全部 index（存在性；`same_seed` 须有历史提交图；`edited_prompt` 须有提示词），置 `starting` 后起**单个后台线程**顺序逐张执行（把 `_redo_one` 的单张主体抽成可顺序复用的函数），每张完成即写 reviews/results，全部结束恢复原状态；新增端点 `POST /api/review/redo-batch` 收 `indexes[]`（其余字段与单张一致，含可选 `seed`）。运行期间状态机天然禁止并发 start/redo。
- **前端**：审图卡片加勾选框；工具条加「全选待审」「打回选中 (N)」；复用 `rejectDialog`（标题列多张编号；`edited_prompt` 在批量模式下禁用——各张提示词不同，不适用统一替换）；进度走现有 progress bar。
- 快捷键不变；「疑似重复」徽标的一键换种子重做走本能力（第 8 项）。

**落实方式**：`comfybatch_v2_core.py`（redo_many + 重构 `_redo_one`）、`comfybatch_v2_app.py`（1 端点）、`index.html`/`app.js`（勾选框、工具条、submitRejectBatch）、`tests/test_review_store.py`+新用例；真机 e2e：2 张 new_seed 批量重做成功且 attempts/history 正确递增（防 ingest 判重现复发，docs 03 的教训）。

## 6. 图片排布更密集

**现状**：`.review-board { grid-template-columns:repeat(auto-fill,minmax(430px,1fr)); gap:14px }`，卡片内缩略图列固定 210px（app.css:641-663）。1920 宽下一屏约 4 张，45 张批次要滚很多屏。

**方案**：三档密度切换，**默认紧凑**：
- 紧凑：`minmax(280px,1fr)`、gap 8px、缩略图 120px、提示词/元数据折叠为单行省略号；
- 标准：现状不动；
- 宽松：`minmax(520px,1fr)`。
切换按钮放 `review-toolbar`，选择存 localStorage；实现为 `.review-board.density-compact/…` 三个 class 段 + `renderReviewBoard` 读偏好，不新增渲染路径。

**落实方式**：`app.css` 三段（约 40 行）+ `app.js` `setReviewDensity()` + `index.html` 工具条 1 按钮；`tools/reformat_frontend.py` 三道闸门照跑。

## 7. 种子调控（核心需求）

**现状**（好消息：后端链路是现成的，缺的只是 UI）：
- `BatchConfig.seed` 已存在：编译时 `apply_seed()` 把提交图里全部具体种子钉为给定值、多采样器按节点 +1 偏移防同种相关（core:299,324,1448-1449；nodeschema:961-973）；`/api/start` 的 body 就是 `BatchConfig.from_dict`，**传 `seed` 字段即可生效，后端零改动**。
- **默认行为已经是「默认变化」**：KSampler/KSamplerAdvanced/UltimateSDUpscale/Seed(rgthree) 四类转换器 `seed_policy="randomize"`，每张图编译时重摇（nodeschema:779-786,622-626）；docs/04 实测：批次固定 123456 → 整批同种子；不固定 → 每张新种子；redo 可显式 pin。
- 卡片已显示每张真实提交种子（从编译图取值，非意图值，app.js:1805-1814）。
- 缺口：前端没有任何种子输入；`submitReject` 不传 seed（后端已支持，app.py:1712-1718、core:2319-2321）。

**方案**：
1. 阶段 2「工作流与模型」deck 加种子控件：`select`（**默认变化**：每张随机 ／ **固定种子**：整批唯一）+ 数字输入 + 「用最近一次的种子」快捷钮；`batchConfig()` 增加 `seed` 字段（空=默认变化）；
2. 固定种子时显示黄色提示：「整批共用该种子（多采样器自动 +1）；提示词相同的任务会产出相同图」——与第 8 项联动；
3. `rejectDialog` 加「指定种子（可选，留空=按模式取随机）」，`submitReject` 带上；`same_seed` 模式下该输入禁用（同种子重做直接重发原图，docs/04 实测像素级一致）；
4. 卡片种子行加「复用」小按钮：一键填入批次种子框或重做对话框。

**边界说明**：种子若在工作流里是**连线**（指向其他节点）则不覆盖——这是「永不覆盖连线」的刻意设计；主力 Krea2 流的 19/20 号采样器种子为控件值，已被 randomize/pin 完整覆盖（docs/04 全部实测）。**落实方式**：`index.html` 2 处 + `app.js`（batchConfig/openRejectDialog/submitReject/seedHtml）约 60 行 + **后端 0 改动**（redo seed 已通）；`test_params`/`test_compiled_graph` 补 seed 字段断言；真机验证沿用 `tools/acceptance/seed_probe3.py` 思路：固定 123456 批次 → 卡片种子全等；redo pin 777 → 复现。

## 8. 防止单一图片大量产出

**现状**：三道已有防线——①每张默认重摇种子（见第 7 项）；②「单人单画面保护」：三栏面板相似度 ≥0.88 判疑似三联图，自动换种子重试（core:745-770,2539-2543，UI 有开关+最多重试次数）；③连续失败熔断+工作流级首条即停。真正的「整批同图」风险只剩一个口子：**固定种子 + 提示词相同**。

**方案**：
1. 固定种子时的黄色警告（第 7 项联动）——事前防；
2. 事后可见：批次结束统计各张 `generation.seeds`，出现「同种子 + 高面板相似度」的行在审图板标「疑似重复产出」徽标，并给「换种子重做选中」（走第 5 项批量重做）；报告 JSON 写入 seeds 频次表；
3. 可选不做：批内逐对图像相似度查重——每对都要读图对比，45 张即 ~990 对，成本高，默认不做，先用种子维度兜底。

**落实方式**：`core` 报告组装段 +10 行统计；`app.js` `renderReviewBoard` 徽标；`test_comfybatch_v2_core` 补统计用例。

## 9. 输出目录不存在时自动新建

**现状**：**启动批次时已经会自动创建**——`/api/start` 里 `pathlib.Path(config.output_dir).mkdir(parents=True, exist_ok=True)`（app.py:1617），core `_run` 开头再兜底一次（core:2440）；`validate_start` 不检查输出目录存在性。所以「指定一个不存在的输出目录→启动→自动建目录并正常出图」这条主链路**今天就通**。
用户能撞到的坑是：①点「打开输出目录」按钮时目录还不存在 → 直接报错「输出目录不存在，请先创建目录或检查路径」（app.py:1846）；②页面上没有任何「会自动创建」的说明，不知道可以先启动。

**方案**：
- `/api/open-folder`：目标目录不存在时先 `mkdir(parents=True, exist_ok=True)` 再打开（磁盘错误/权限错误仍如实报）；
- `batchOutputDir` 帮助文案改为「目录不存在时会在启动批次时自动创建」；preflight 成功后 effective 面板显示输出目录终值。

**落实方式**：app.py 约 5 行 + app.js `openBatchOutput` 提示 + index.html 文案；`test_app_routes` 补用例：对不存在路径调 open-folder → 200 且目录已建。
