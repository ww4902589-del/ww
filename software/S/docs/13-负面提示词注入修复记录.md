## P0-2：语义变更警告

**问题**：采样器 `negative` 口挂的不是 `CLIPTextEncode`（如 `ConditioningZeroOut`，表示"不做负面引导"）时，填写负面词会**静默**把作者的设计换成"真正的负面引导"。`errors`/`warnings` 全空。

**修复**：新增 `_negative_anchor_types(workflow, config)`，**同时支持 API 图与 UI 图**：

- API 图：`inputs.negative` 直接是 `[node_id, slot]`
- UI 图：`inputs` 是列表，`negative` 是 **link id**，需经 `links` 表解析到目标节点

返回**非 `CLIPTextEncode`** 的锚点类型（去重），在 `capabilities()` 中转为 warning：

```
该工作流的负面条件原本由「ConditioningZeroOut」处理，填写负面提示词后将改为
直接负面引导；若原作依赖该节点（如归一化负面以关闭负面引导），出图效果会随之改变
```

**不改变注入行为**——只是把已经发生的事说出来。

同时报告新增 `negative_prompt.replaces`（类型列表），供前端展示。

**验证**：真实工作流实测 `replaces: ["ConditioningZeroOut"]`、warning 非空；正常接编码器的工作流 `replaces: []`、warning 为空。

**收录的替代节点类型**（`NEGATIVE_SURROGATE_TYPES`）：`ConditioningZeroOut`、`ConditioningSetArea`、`ConditioningSetAreaPercentage`、`ConditioningSetMask`、`ConditioningCombine`、`ConditioningConcat`、`ConditioningAverage`、`ConditioningSetTimestepRange`。

## P1：负面编码节点复用

**问题**：`_apply_prompt` 按采样器循环，`updated_encoders` 去重集合**只在"就地改写"分支写入**，"新建"分支不参与 → 每个采样器各建一个内容相同的节点（实测 `[30]`、`[31]`）。

**修复**：新建分支引入 `injected_by_key: dict[tuple[str, str], str]`，key = `(negative_text, json.dumps(clip_link))`。文本与 CLIP 来源都相同才复用；任一不同仍各建一个（这是正确的——不同来源不该强行合并）。

**验证**：该工作流从 2 个重复节点降为 1 个（`run/_verify_negative.py` 输出 `节点数: 1`）。新增测试 `test_a_single_negative_encoder_is_shared_by_every_sampler` 断言两个采样器指向**同一个**节点 id。

## P2：内置控件顺序兜底表

**问题**：`CLIPTextEncode` 不在 `CONVERTERS` 里，走通用 widget 绑定。若图**既没有 `widget` 声明、注册表也查不到该类型**，`declared=[]`、`strategy='none'`，`widgets_values` **完全不被绑定** → 负面编码的 `text` 为空 → 负面词静默丢失。

> **范围说明**：真实 ComfyUI 导出的 UI 图**自带** `inputs[].widget` 声明（实测 "Node name for S&R" 段落），所以**真实工作流不触发**此问题。它只在手写或第三方转换的图上出现。修它是为了消除"静默降级"，与本项目"不能安全改就报错"的原则一致。

**修复**：新增 `BUILTIN_WIDGET_ORDER`，在 `NodeSchemaRegistry.widget_order()` 里作为**最后兜底**（schema 永远优先）使用。

### ⚠️ 实现中的关键坑（勿重蹈）

第一版把 `control_after_generate` 写进了表里，**测试直接炸**：

```
ValueError: could not convert string to float: 'euler'
```

原因：`_align_with_reason()`（`nodeschema.py:493`）**已经按位置**在 seed 之后插入隐藏的 `control_after_generate` 槽位。它基于**声明顺序**工作，所以表里必须给出**声明顺序**，**排除** `control_after_generate`。

真实数据佐证（`KSampler`）：

| 来源 | 内容 |
|---|---|
| `widgets_values`（7 项） | `[seed, "fixed"/"randomize", steps, cfg, sampler_name, scheduler, denoise]` |
| `inputs[].widget`（6 项） | `[seed, steps, cfg, sampler_name, scheduler, denoise]` |

**表必须照抄右列。** 表里每个条目都加了注释说明这一点。

**验证**：新增 2 个测试——`test_builtin_order_covers_core_nodes_when_the_node_declares_nothing`（无 widget 声明的 `CLIPTextEncode` 与 `KSampler` 都能正确绑定）、`test_the_schema_still_wins_over_the_builtin_table`（schema 优先，未知类型不借用别人的顺序）。

## P3：孤立 conditioning 节点标记

**问题**：负面口被改指后，`ConditioningZeroOut` 失去全部消费者，但仍留在图里。

**修复**：`_apply_prompt` 记录 `self.last_orphaned_conditioning`（`{node_id: class_type}`，在 `build()` 两条路径入口重置），经 `audit()` 输出：

```json
"orphaned_conditioning": [{"node_id": "15", "node_type": "ConditioningZeroOut"}]
```

**只标记不删**——该工作流含 3 个 rgthree `Fast Groups Bypasser (rgthree)`，分支可被重新启用，删除会误伤。测试断言节点仍在图中。

> 为让 `_apply_prompt` 能写实例状态，它从 `@classmethod` 改为实例方法（内部仍用 `cls = type(self)` 调用类级辅助函数）。
