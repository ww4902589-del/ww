## 2. 工作流参数能否自动映射 —— ✅ 方案A 已实施（2026-09-19 22:16）

### 现状（读代码核实）

**没有"自动映射"这个功能**，现有的是两层：

| 层 | 位置 | 行为 |
|---|---|---|
| **按名绑定** | `comfybatch_nodeschema.py` `WidgetBinder` | 按**控件名**把 `widgets_values` 绑到 `inputs`。这是"值能不能正确写进去"，不是"参数能不能自动填"。 |
| **按指纹记默认值** | `comfybatch_v2_core.py:2746` `WorkflowParamsStore` | 用户手动设过"工作流默认值"后，按 `structural_fingerprint` 存起来，下次同一工作流自动带上。`remember()` 是 `{**existing, **values}` 合并。 |

也就是说：**软件不会自己去"猜"你的参数意图**；它只会忠实复现你上次明确保存过的值。

### 为什么不做"真自动映射"

"自动映射"隐含"软件替你决定参数值"。本项目的第一原则是**不静默改用户的东西**——
`docs/01` 里那条"按位置猜参数在原理上不可能正确"的教训还热着。真做自动映射，
就得在"猜错"和"多问一句"之间选，而猜错的代价是出一批你不想要的图。

### 方案（按侵入度递增）

| 方案 | 内容 | 适用 | 代价 |
|---|---|---|---|
| **A（建议·保守版）** | **继承上次值**：用户手动改过的参数，如果没保存为默认值，仍按"仅本次批次"生效；但提供一个开关"记住这次的参数"，勾上即等于现有 `remember()`。本质是把已有能力**显式化**，不新增猜测逻辑 | 想"少点一次" | 小 |
| B | **同类工作流迁移**：换了工作流但节点类型相同（如都有 `KSampler`），提示"检测到 6 个可比参数，是否沿用上次的值？"，用户点确认才写入 | 常切工作流 | 中 |
| C | **从 `object_info.json` 推断**：用节点 schema 的 `min/max/default` 把没设过的参数填成节点默认值 | 想要"开箱即用" | 中，且**风险最高**：会把作者的默认值覆盖成注册表的默认值，两者未必一致 |

**建议 A**，需要的是一次确认；B 可以作为下一步；**C 不建议**，与本项目原则冲突。

### 2.1 实施：方案A「记住这次的参数」（2026-09-19 22:16）

开关只做一件事：把已有能力**显式化**——勾上后应用，等于现有 `WorkflowParamsStore.remember()`，零新增猜测逻辑。

| 层 | 改动 | 落点 |
|---|---|---|
| UI | `.wb-scope` 新增「记住这次的参数（保存为该工作流默认值）」复选框，**仅在"整个批次"作用范围下显示**（`rememberWrap.hidden=scope!=='batch'`）；选"保存为工作流默认值"时隐藏（它本身就是记忆） | `index.html`、`app.css`（`.wb-remember` + `[hidden]` 覆盖规则，遵守 hidden 切换守卫） |
| 前端 | `applyWorkbench()` 在 batch 范围且勾选时请求体带 `remember:true`；成功反馈区分「本次批次生效，并已记住为该工作流默认值」 | `app.js` |
| 后端 | `/api/params/apply` 新增 `scope=="batch" 且 remember` 分支：与 `scope=="workflow"` 完全同构（校验通过的值 `remember()` 合并保存；清空的键从已存默认值 `forget()`），不通过校验的值照旧不落盘 | `comfybatch_v2_app.py` |

**语义边界**：不勾＝行为与从前完全一致（仅本次批次，关闭页面即失效）；勾上＝这一批的值同时成为该工作流的默认值，下次同工作流自动带上。指纹变了照旧不自动迁移（`stale_for` 的既有警告不变）。

**测试**（376 项全过）：`test_batch_scope_remembers_only_when_the_switch_is_on`（不勾不落盘 / 勾上落盘）、`test_remember_this_params_switch_is_wired`（开关标记与接线）、hidden 守卫测试反向抓出 `.wb-remember` 初版缺 `[hidden]` 覆盖（已修）。

### 风险

### 6.1 负面提示词：能不能"接入"没有编码的工作流 —— ✅ 方案A+C 已实施（2026-09-20 00:26）

**放宽方案：**

| 方案 | 内容 | 代价 | 风险 |

| **A（建议）** | **CLIP 来源就近回退**：借不到时，在**全图**范围内找任意一个 `CLIPTextEncode` 或 `CLIPLoader`/`CheckpointLoaderSimple` 的 `CLIP` 输出，作为补建节点的来源；**但在审计里标明"CLIP 来源为回退所得"** | 小～中 | 低（回退是显式记账的） |

### 6.2 节点注入：风格组合节点等能注入没有它的工作流吗 —— ✅ 方案A 已实施（2026-09-20 01:36）

**现状：只支持两类注入，都是"接线式"，不是通用节点注入。**

| 已支持 | 位置 | 做法 |
|---|---|---|
| LoRA 注入 | `_inject_loras`（`core.py:1748`） | 在模型链/CLIP 链上插 `LoraLoader` |
| 原生风格注入 | `_apply_native_styles`（`core.py:1637`）、`_record_injected_styles`（`core.py:1382`） | 写进已有编码节点，或记下注入来源 |

**没有**的能力：`_bypass_style_nodes` 这套"绕开/插入"逻辑**只对已识别的风格节点类型生效**，
不存在"往任意位置插一个任意节点"的通用机制。这是**有意的**——通用注入需要知道
"插在哪、插进去之后谁读它的输出"，这两件事在图上是不可猜测的。

**方案（白名单式，而非通用式）：**

| 方案 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **A（建议·已确认范围）** | 定义**可注入节点的白名单**，每个条目自带三件事：① 类型；② 锚点（插在哪个输入口，如 `model` / `clip` / `conditioning`）；③ 谁消费它的输出（重指哪个下游口）。**范围限于风格类** | 中～大 | 中：白名单外仍拒绝，安全边界清楚 |
| B | 通用节点注入（用户手选插入点） | 大 | **高**：等于把图编辑权交给用户，出错难定位 |
| C | 只把风格注入**扩到更多已有类型**（不做真正的"组合节点"） | 小 | 低 |

**用户已确认：只做风格（2026-09-19 20:12）**

这条**收窄了白名单的边界**，而且是好事：

- 白名单**第一批只收风格类节点**（风格组合、风格选择器一类），**不**扩到放大、修脸、ControlNet 等。
- "只做风格"意味着锚点契约可以**收敛到一个形状**：输入必须来自 `conditioning`/`clip` 链，
  输出必须汇回同一个采样器的 `positive`。**不需要**为不同用途设计不同的锚点类型。
- 这也让白名单条目**可枚举、可审计**——风格节点的接线方式在 ComfyUI 生态里本来就高度同构
  （`easy stylesSelector` 这类已在本项目测试里出现过），比一个通用插槽可靠得多。

**建议 A（范围=风格类）**。这是把"风格组合节点"做成**有明确契约**的能力，而不是一个万能插槽——
`docs/01` 的教训是"猜测位置会出错"，那么注入就必须带**显式的锚点契约**。

#### 6.2.1 实施：白名单式风格注入（2026-09-20 01:36）

用户答复「可以」（01:07）后实施。落地形状与预设一致，锚点契约**比预设更进一步收窄**：

**白名单（`core.py` 类常量 `STYLE_INJECTION_WHITELIST`）**——首批唯一条目 `easy stylesSelector`：

| 契约字段 | 值 | 说明 |
|---|---|---|
| ① 类型 | `easy stylesSelector` | 字符串级组合器：文本进、文本出 |
| ② 锚点 | 宿主 `KSampler`/`KSamplerAdvanced` 的 `positive` 口**直连** `CLIPTextEncode` | 组合器链输出汇回该编码器的 `text` 口（③ 消费口），正面链其余部分不动 |
| ③ 消费口 | 同一编码器的 `text` 输入口 | 不是 conditioning 口——节点语义决定锚点形状，契约照实收窄 |

**行为变化（对照 §6.1 前的旧实现）：**

| 场景 | 旧行为 | 新行为 |
|---|---|---|
| 原生模式 + 锚点满足 | 注入组合器链 | 不变（行为一致，改为白名单驱动 + 台账） |
| 原生模式 + 全部采样器锚点不满足 | **build 时抛错**「无法启用原生风格组合器」（capabilities 却预告"原生组合器"，预告与行为不一致） | **回退为提示词编译**（`apply_style_templates` 与 compile 共用一份合并实现），warning 明说锚点不满足、已改编译；回退同时绕开作者自带的风格组合器，避免双重风格 |
| 原生模式 + 部分采样器锚点不满足 | 未命中的采样器**静默**不应用风格 | 注入照常覆盖命中者；audit `unanchored` 逐台记名 |
| 注入挤掉编码器 text 口原有连线（如作者的组合器） | 静默孤立，无记录 | audit `displaced` 记名；节点保留不删 |
| 锚点与模板文字双双缺失 | build 抛错 | capabilities 预检即拒，错误写明「不满足原生风格注入的锚点契约」 |

**记账（audit `style_injection`）**：`mode`（原生组合器 / 编译回退（原生锚点不满足））、`hosts`
（锚点命中的 采样器→编码器）、`unanchored`（未命中采样器→其 positive 来源类型）、
`injected_nodes`（本次注入的节点 id，逐个标记 `SOURCE_INJECTED`，API 图与 UI 图一致——
取代旧 `_record_injected_styles` 的启发式）、`displaced`（被挤掉的 text 来源）。

**capabilities 同步**：`style` 载荷新增 `native_anchor` / `native_fallback`；预告与 build 共用
同一份锚点评估（`_style_anchor_hosts`，API/UI 图通用），不再许诺构建做不到的事；
真相栏风格行在回退时追加「 · 原生锚点不可用，已改编译」。

**测试（新增类 `NativeStyleInjectionTests`，5 项）**：白名单条目契约完备性；锚点缺失→编译回退
（含 capabilities 预告与 audit 断言）；部分命中→只覆盖命中者并记名未命中者；锚点+模板双缺→
预检即拒；注入挤掉作者组合器→`displaced` 记名且节点保留、注入节点标记软件注入。

**验证三层全绿**（01:36）：`run_tests.py` **383 项**（过 382 / 败 0 / 跳 1，376→383 净 +7：
§6.1 +2、本轮 +5）；`snapshot_frontend.py` 结构一致；DOM harness 11/11。重新打包随 S.exe 分发。
